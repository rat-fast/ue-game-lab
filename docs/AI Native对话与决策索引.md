# AI Native 对话与决策索引

## 文档用途

本文档把 Codex 本地任务历史中与本仓库直接相关的讨论，整理成可检索的决策索引。它不是对话逐字稿，也不替代根目录的 `AI_NATIVE_GAME_DEV_PRINCIPLES.md`、学习地图或具体项目文档。

整理基准：2026-09-04。

对话记录仍以 Codex 本地任务历史为原始来源；本文只保留已经影响仓库结构、项目方向或后续行动的内容。没有证据支持的推测不写成项目事实。

## 当前总判断

我们现在有两个不同职责的 UE 项目：

- `ue/AINativeRoguelite/`：较完整的 UE 学习和已有内容参考项目。当前没有项目本地 `Docs/README.md`，进入该项目时应以真实源码、配置和资产为准。
- `ue/SkillLab/`：新建的技能领域实验项目，用来验证 AI 是否能在受约束的技能领域内完成理解、设计、实现、验证和迭代，不以做成完整游戏为目标。

根目录原则不需要因为新增 `SkillLab` 而整体重写。当前更需要的是把原则落到项目边界、实验产物和验证证据上。

## 当前架构假设与边界

以下是实验假设，不是已经锁定的最终架构：

```text
稳定运行能力       → C++ / 可复用组件
技能参数与重复内容 → 配置 / 结构化数据
复杂行为组合       → 领域 DSL、行为图或可执行中间表示（待验证）
UE 对象与表现连接   → Blueprint、动画、Niagara、音频等适配层
成熟技能后端       → GAS 作为候选，不是当前前置条件
复杂且高变化逻辑   → 受限脚本作为后续候选，不在当前第一步引入
```

关键边界：

- 数据驱动不等于简单配表。数据可以逐步表达参数、组合、条件、时序和嵌套，但不能凭空创造运行时尚未实现的原语。
- 可执行 DSL 不能因为是文本就自动优于 C++ 或 Blueprint；它只有在减少重复、支持批量生产、便于校验并改善 AI 生产效率时才有价值。
- 直接修改 Blueprint 的效率问题是需要验证的事实，不能通过假设“AI 熟练以后会变快”来跳过接口审计。
- GAS 解决的是通用 Gameplay 运行能力，不等于技能设计方法，也不等于 AI Native 生产接口。
- 脚本层可能适合复杂、频繁变化的业务逻辑，但会引入运行时、沙箱、调试、版本和性能成本；应在已有运行框架和真实瓶颈明确后再做小实验。

## 已有证据、未决问题和下一步

### 已有证据

- `SkillLab` 已有项目自己的最小运行地图、角色、输入、GameMode 和导航测试文档。
- `L_SkillLab_NavTest` 的点击移动、绕障和成功/失败反馈已在 PIE 中得到用户确认；相关证据记录在 `ue/SkillLab/Docs/Modules/LevelAndDebug.md` 和 `Navigation.md`。
- 直接通过 MCP 逐节点修改 Blueprint 的方式在简单流程上效率较低，这是选择数据或结构化生产接口的重要动机。
- GAS 的第一轮学习已经完成若干核心对象和运行链梳理，但 `SkillLab` 尚未因此接入 GAS。

### 未决问题

- 一个代表性复杂技能实际需要修改哪些产物，哪些产物 AI 能可靠读取、修改和验证。
- DataTable、DataAsset、外部 JSON、领域 DSL、可执行 IR 和受限脚本之间的真实收益差异。
- 技能行为的复杂度、可调试性、网络需求和表现接入是否会改变后端选择。
- 哪些重复判断值得固化成 schema、工具、模板或自动化；目前不能只凭一次演示决定。

### 推荐下一步

1. 维持 `SkillLab` 的最小运行基线，不急于扩大成完整游戏。
2. 选定一个包含时序、目标、伤害、Buff、飞行物和最小表现反馈的代表性技能。
3. 先人工走一遍传统实现链，再逐项记录 AI 的读取、修改、验证效率和失败点。
4. 依据证据决定哪些内容进入 C++、配置、领域结构、Blueprint 适配层或后续脚本实验。
5. 只有当输入、输出和验收稳定后，才固化 schema、工具和批量生产流程。
