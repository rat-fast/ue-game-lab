## 资源 GE 与兼容 API 的授权边界

需求 `SkillCombatRulesRequirements.md` 第 8.1 节规定的是资源预留、实际/可用余额和未决结算等行为不变量；在需求正文中检索不到 `RequestResourceEffect` 这个 API，也没有指定“完整 GE 语义应由此入口承载”。需求支持解决 Energy/MaxEnergy 写入破坏预留的问题，但没有批准某个具体函数名或 GAS 实现方案。

原始 `VerificationHandoff.md` 的 R 职责（当前文档第 40–45 行）授权消费审计发现，把正式资源写入纳入现有协调器，或在加载/应用前拒绝不合法配置；并明确保留 `RequestResourceChange`、reservation、唯一 Resolve 与结算历史。该任务范围支持 R 在已授权 GAS 文件内实现资源一致性修复，但没有逐字指定新增兼容 GE API，也没有授权全局关闭与资源无关的 GE execution。

`RequestResourceEffect` 的具体窄契约在交接第 98 行出现为“保持”既有接口：只转换纯即时单资源数值 spec，不产生 GE handle、不执行 calculation 或其他 GE 语义。`ResourceWriteImplementationSummary.md` 第 10 行记录了同一契约；源码中定义位于 `SkillLabResourceEffects.cpp`，本仓库当前检索到的直接调用只有资源集成测试两处（`SkillLabResourceWriteIntegrationTests.cpp` 约第 237、243 行），没有正式非测试调用者。因此证据支持把它描述为实现阶段采用并由后续交接保留的兼容适配选择；没有找到更早的用户原话或需求条款逐项批准这个 API。留存日志也不足以可靠确定第一次提出/写入该符号的具体 Agent 与时间，不将缺少证据说成用户曾明确批准或明确反对。

GE 拒绝范围则有明确的纠偏证据。C1 的只读资源审计分别证明：动态资源 GE 与持续 MaxEnergy 聚合可能破坏预留，但这些是隔离测试夹具，不是已发现的生产配置；正式伤害/治疗 GE 不直接修改 Energy。随后 R 交接局部核对（第 90–100 行）指出实现中的“Executions 非空就拒绝”会连无关非资源 execution 一起拒绝，超过需求 8.1 的资源保护目标。架构指令要求保留静态直接资源 modifier/持续资源聚合的生效前保护，改为在 `CombatAttributeSet::PreGameplayEffectExecute` 按实际输出属性拦截 Energy/MaxEnergy，非资源输出维持既有 GAS 语义；并明确逐项 veto 不保证整个混合 GE 原子回滚。

据此应作如下区分：

- 用户/需求授权的是资源一致性目标及完成该批功能的程序工作，不是 `RequestResourceEffect` 的特定 API 设计。
- “纯即时、单资源、无额外 GE 副作用”的适配契约是实现/架构层的窄兼容方案。R 被授权在 GAS 内落实资源协调或生效前拒绝；设计这个窄适配入口属于该实现任务内的技术裁量。没找到更早的逐字 API 批准，不足以单独判定越权。
- 拒绝会改动 Energy/MaxEnergy 的静态资源 modifier 或持续资源聚合，有保护预留的需求依据；一概拒绝所有 execution 扩大到了无关属性。架构核对已明确要求缩窄，并保留非资源效果。
- 当前测试夹具证明通用边界行为，不证明生产内容正在调用该兼容 API，也不证明所有动态或原生写入都能被拦截。
