# SkillLab 代码质量关口补查

本报告接续 `CodeInvestigation.md`、`CodeInvestigationFollowup.md`，只回答五类已定位问题为何仍在当前代码、架构与 Review 的落盘证据是否识别或闭合它们。调查跨上海时间 2026-11-12 至 11-13，沿用原调查目录；实际封存时间见 `CodeQualityGateAuditCheck.json`。

## 1. 直接回答

**部分残留确实不应作为本轮迁移的最终质量状态留下。** 仅写不读字段，以及去重迁移后仍为计数保存完整结果，是有具体读写证据的无效状态或冗余存储；它们处于本轮修改的执行/资源边界，应该被实现自查和独立 Review 识别、收束或明确记录接受理由。功能测试通过不能替代这一判断。

但另外三类不能同等定性：

- 测试专用生产 wrapper 是实际兼容接缝，有真实测试用途，并非无效代码；是否应留在生产编译范围、是否应走这个私有入口，属于应明确审查的边界选择。仅凭“服务测试”不能认定功能缺陷。
- 终态历史保留有当前生产消费者，未决、去重、晚到结果要求它长于 Cast；无会话内裁剪不等于已证实泄漏。缺的是足以判断规模是否可接受的寿命/容量依据，不能自行设保留时长后反判不合格。
- 新旧 fixture 并存不天然错误；本次有实际迁移成果，但旧大测试仍多职责、重复目录恢复也仍在。已有局部迁移要求的最终符合性和例外理由，没有在当前落盘 Review 中得到充分闭合。

**“有架构、有 Review”在本次不是“已做过并通过所有结构质量检查”的证据。** 架构交接对所有权、分层、共享测试迁移有明确要求；原 Review 核对功能链、识别并关闭实质重入缺陷，也追查了 Reset 验证缺口。与此同时，落盘材料没有点名本报告的残留字段、结果重复、wrapper 或历史裁剪问题，也没有逐项说明旧测试组织的收束状态。可以判断这些具体质量项在交付证据中未闭合；不能据此断言历史对话从未看过，更不能推定某人明知而忽略。

无参 `USkillLabLuaSkillBehavior::ExecuteDeclaredAction()` 在 HEAD Behavior 头/实现没有，本轮新增。当前声明位于 `SkillLabSkillBehavior.h:74` 的 **private** 区域，由 friend `FSkillLabProductionFixture` 调用，不是面向游戏内容公开的入口。生产编译中存在实现，未被 `WITH_DEV_AUTOMATION_TESTS` 隔离。

`SkillBehaviorProduction.cpp:9–22` 通过当前 production point 修改点上下文、LastPointId/LastResponse，并调用带参实际动作；唯一无参调用在 `Tests/SkillLabProductionFixture.h:120`。正常玩家链在 `SubmissionPointExecution.cpp:91` 调用带参版本。注释直接说明是旧失联回执 fixture 适配。

它的必要用途是测试可控丢失同步返回、真实生产行为仍发生；不是伪造接受/扣款，也没有独立复制状态机。因此不宜称“明确无效代码”，也不能由一般“测试适配分开”规则推导一切测试接缝都必须不参与生产编译。

**当前应识别的是局部质量选择：为什么测试专用、会改状态的兼容接缝留在生产类，是否绕过应验证的正常点请求前置，以及其用途和限制如何接受。** 现有端到端测试不能由这个 wrapper 单独替代，架构交接也已提示直接 Begin/Execute 不算最终正式证据。可判编译/维护面增加，不能判已有玩家漏洞或整个测试无效。是否保留需具体程序边界判断，不需重新决定玩法，也不能仅凭用户希望“无残留”就删除有效测试能力。

### 3.4 终态历史无裁剪：确有增长结构，缺陷结论有限

`SubmissionResults`、ASC reservation/settlement history/资源 ID 集合、会话 `Records/PendingFeedback` 在所比 HEAD 均未检出，本轮未提交阶段新增。当前代码存在这些有生产用途的保留：

## 5. 为何有架构和 Review 仍留下：能证明的解释与不能归责的部分

从产物能解释到以下层次：

1. **迁移以接通新所有权/行为为中心，旧状态随对象搬迁。** 旧结果数组的实际读者迁走、存储仍保留，是可直接复原的代码变化；其他死字段也被带入新状态或新增协调器。这说明迁移后消费者核对不足，不能说旧状态都因有功能需求而必要。
2. **测试兼容与可编译被实现，结构迁移的验收没有同样具体。** 有真实共享 helper/独立测试，也保留有状态 wrapper 和多处目录恢复。摘要的“迁到唯一执行观察”证明观察适配，不自动证明基础夹具职责已经统一。
3. **Review 记录强调功能不变量、真实验证和版本证据。** 首次报告实际查出 P2-CE-1，后续又指出 Reset 合法拒绝论证漏掉 Health 回调，均不是只看绿测试。然而这些有效核对不包含每个状态字段消费者、完整结果存储成本或测试接缝边界的落盘结论。
4. **范围排除了全面结构审计，但局部结构验收没有明确分账。** README:13 写全面结构审查不在本轮，Review:44 写未做全仓结构质量审计；这可以限制扩审，不能自然豁免本轮实质修改、架构明文交接的迁移职责。是否有原始消息进一步批准延期，必须查原文。
5. **历史容量没有当前定量合同。** 功能需求促成长期保留，但材料没有给出裁剪安全条件或规模预算；这类问题即使被注意，也不能像删除无读者状态那样直接裁定。其风险可能被功能讨论遮住，但“没人意识到”仍是未经历史核实的推断。

因此可判**局部质量关口覆盖及交付说明不足**，不能判“有 Review 就应该绝无遗漏”，也不能把覆盖不足洗成“功能通过，无所谓”。当前证据不支持揣测 Agent 动机、以对话数量解释失误，或直接指定某个角色未履职。

## 6. 当前交付可以证明什么，不能证明什么

架构产物可以证明有明确每 Cast/Runtime/ASC/Behavior 分工、当前运行链复用判断、测试迁移要求和分层接口；不证明实现逐字段遵循，更不证明所有新状态最小。通用规范已要求结构与复用、机制/测试适配分开，但“单一内容权威”不能机械解释成任何投影/结果快照都禁止。
