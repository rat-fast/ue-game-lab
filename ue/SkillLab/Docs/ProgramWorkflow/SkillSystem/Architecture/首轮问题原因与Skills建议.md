# 首轮问题原因与 Skills 建议

本文只记录对 `.codex/skills` 的改进建议。本轮不修改任何 Skill 文件；建议由维护者另行评估。

## 总控

首轮任务缺少“当前接口契约必须先于实现”的强制核对，导致实现先围绕单个样例技能推进。建议总控交接模板在派发前列出身份、授予、目标、结果终态、事件快照和验证命令，并要求回收时逐项给出证据。

## 架构

首轮架构已定义 `GrantedAbilityId`，但实现阶段没有把它与 GAS SpecHandle 的区别作为阻塞检查；TargetSpec 和第二技能复用也没有进入最小验收矩阵。建议架构 Skill 将业务身份与引擎句柄分离、目标可验证性和至少一个第二技能复用列为冻结契约。

## 模块实现

首轮实现容易把 `bSkillGranted`、单 Ability 扫描和样例请求入口当作足够抽象，原因是缺少“按 SkillId 授予/查找”的代码级验收项。建议实现 Skill 要求提供默认装配列表、授予记录结构和第二定义静态接入证明，并扫描禁止的单技能状态字段。

## 集成

首轮集成只需要一个 Pulse 载体，未要求第二个不同属性语义的载体，因此复用边界没有被真正验证。建议集成 Skill 增加“第二技能只改定义/载体/装配/测试适配”的最小接入检查，并验证模块文件被 Build.cs 自动收集。

## 验证

首轮运行证据缺少命令入口覆盖、数值结果可观察性和失败目标上下文；旧日志曾被误认为当前证据。建议验证 Skill 强制记录实际命令、实际日志文件、每个技能的 `GrantedAbilityId/TargetUnitId/EffectResult.Status`，并明确命令行与 PIE 的证据边界。

## Review

首轮 Review 发现了硬编码、专用入口和身份缺失，但这些问题在早期没有作为代码扫描规则固化。建议 Review Skill 对单技能布尔状态、按 AbilityClass 扫描、无目标单位身份、Completed 与效果成功混淆、以及文档把历史状态写成当前事实建立固定检查项。
