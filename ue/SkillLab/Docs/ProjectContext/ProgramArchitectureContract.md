# SkillLab 程序分层约定

本文是 SkillLab 程序架构、实现、集成和 Review 的项目级约定。它规定职责边界，不要求固定类名、目录、框架或每项功能都必须新增三层。

## 三层职责

1. **稳定运行内核**：以可复用的 C++ 能力实现生命周期、状态转换、校验、调度和运行时接口。它表达稳定机制，不直接承载某个技能或内容条目的专属参数与分支。
2. **脚本化组合层**：基于运行内核已有接口组合具体行为、流程或能力。它可由 C++、Blueprint 或项目实际采用的脚本技术实现；技术语言不决定职责层级。新增或修改时应接入既有接口，不复制底层机制，也不把单个内容实例硬编码进通用内核。
3. **文本配置层**：承载需要频繁调整、批量维护或被工具处理的参数、资源引用和内容声明，使用项目已有的 JSON、其他结构化文本或生成源。它不承担生命周期与业务执行，不通过重复维护形成第二个事实来源。

## 使用边界

- 先从需求识别哪些内容稳定、哪些行为需要组合、哪些值需要独立调整；按实际需要使用这些层。简单需求可以只触及现有层，不为满足形式而新增空壳。
- 先检查项目当前已有的接口、模块和内容入口。优先在职责匹配的现有位置扩展；只有现有边界确实阻碍需求或造成耦合时，才提出迁移或新增切入点。
- 层与层之间通过明确、窄化的接口连接。调用方不应依赖其他层的内部细节；具体技能、资源或参数变化不应迫使稳定内核增加内容专属分支。
- 同一字段或内容只有一个权威来源。若文本源需要生成 C++、Blueprint 或 UE 资产，需说明生成/导入入口和必要校验；不要求为尚不存在的流程预建工具链。
- 不为抽象本身增加框架、注册系统、通用工厂或验证设施。只有当前需求需要且现有项目能力不足时才引入，并说明其具体用途。
- 复用仓库已有能力；新职责无法由现有能力合理承载时再新增，避免重复实现以及把互不相关的职责堆进同一文件或对象。

## 架构交接要求

面向实现的架构交接说明：需求会经过哪些现有运行环节、可复用的接口/模块是什么、建议的最小修改落点及其层级职责、层间数据或调用边界、需要读取的具体文件，以及尚未确定且会改变实现的事项。只写与当前需求相关的结构判断，不预先设计未来完整系统，也不把当前类名或方案冻结为永久规范。

实现 Agent 可根据源码核对发现交接与事实不符；若差异会改变职责边界、公共接口或需求行为，应带着事实和最小选项回交，不自行扩展架构范围。
