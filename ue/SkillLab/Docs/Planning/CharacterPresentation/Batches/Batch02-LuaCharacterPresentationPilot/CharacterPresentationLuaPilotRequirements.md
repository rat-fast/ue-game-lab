# Lua 角色表现试点策划需求

## 1. 目标与边界

本需求把角色表现主流程作为 Lua 试点：玩家能看到角色的基础行动状态，技能发起后出现与真实施法事实一致的动作响应，动作/特效反馈能表达对应的运行结果，取消或完成后回到正确的基础表现。Lua 是本次已选定的试点脚本语言；策划只规定要表达和验收的体验，不选择其 UE 接入与实现形态。

试点应沿用 UE 动画系统完成动画资源求值、姿势混合、骨骼融合和压缩。必要的 Blueprint、动画及其他 UE 资产可继续保留或由 AI 修改。本需求不要求移除所有 C++/Blueprint，不扩展成全游戏脚本迁移，不改变 GAS 核心、目标/命中/效果/扣费规则或技能生命周期语义。

## 2. 依据分级

### 共享基线已确认事实

- 表现读取技能运行层的结构化事实。`Started`、阶段变化、目标/命中、效果、持续伤害、取消和完成是不同事实；表现不裁定施法、命中、扣费、效果或完成。
- 角色基础状态快照覆盖 `Idle`、`Move`、`Jump`、`Fall`、`Land`。技能动作与基础移动表现可分离，技能动作结束后应回到基础姿势；正式入口中的视觉质量、迁移完整性和结束恢复仍没有本轮验收证据。
- 一次动作关联一次施法身份。旧施法的迟到事件不能清理或改变新施法；取消和完成只影响对应施法。
- 技能动作终止与独立持续效果分开。燃烧等持续效果按技能系统事件持续或结束，动作结束不等于效果结束。
- 四项技能业务差异已确认：火球为敌方单位目标的投射物伤害；区域爆发为敌方地面位置范围伤害；修复为自身即时治疗；燃烧为敌方单位持续伤害。
- 基线资产中记录有角色 Mesh/Skeleton、Idle/Walk/Jog/Jump 等基础动画，以及四项技能动作路径。文件或路径存在不证明可播放、兼容、内部事件有效或已通过视觉验收。
- 当前范围标记、目标标记、数值和持续状态反馈是临时占位表现，不构成正式 VFX、音频、美术或本地化契约。没有正式 VFX 绑定或体验规范的确认事实。

### 用户新增方向

- 以 Lua 试验项目级角色表现逻辑的文本表达和维护流程。
- 以角色表现主流程为试点，覆盖基础角色行动/待机、技能发起后的表现响应、动作与特效的可观察关联，以及取消/完成后的恢复。
- 完成策划需求后交由程序侧 PM 接手评估实现并尽量跑通；本需求因此提供可观察要求和业务验收，不替程序回答实现问题。

### 待定表现选择

- 受击动作是否进入本试点，以及它与基础移动、技能动作的优先级、打断和恢复规则。
- 各技能具体动作风格、长度、释放节奏及玩家可接受的对齐方式。
- 命中、治疗、范围作用、持续效果附着/移除需要哪些正式 VFX，及其资源、视觉语言和持续时间。
- 动作或 VFX 不可用时的最低可接受反馈，以及是否向玩家显式提示内容缺口。
- 取消/完成后是立即恢复基础动作还是保留收招；独立持续效果存在期间角色动作与效果反馈如何并存。

## 3. 阶段与优先级

| 阶段 | 优先级 | 范围 | 退出条件 |
| --- | --- | --- | --- |
| 基础表现主流程 | P0 必须 | 默认可控角色的 `Idle`、`Move`、`Jump`、`Fall`、`Land`；基础状态驱动事实与可见结果可对照 | 明确运行入口可复现状态进入/离开及已知边界；没有把业务结果交给动画推断 |
| 火球纵向验证 | P0 必须 | `Started`/前摇、角色动作、释放/命中或未命中、完成/取消的关联 | 同一施法身份下事件和可见结果可追踪；命中结果来自技能事实，视口与事件证据齐备 |
| 三项差异化迁移 | P1 必须 | 区域爆发、修复、燃烧分别体现其地面范围、即时治疗、持续伤害事实 | 每项按其业务差异验收；燃烧动作结束不使持续效果提前结束 |
| 取消/完成与恢复 | P1 必须 | 前摇取消、释放后取消、正常完成、连续新旧施法；恢复基础表现且隔离持续效果 | 旧事件不影响新动作，恢复可见，持续效果生命周期与动作清理独立 |
| 受击表现 | P2 候选 | 受击动作及其与基础/技能表现的打断关系 | 用户确认体验范围与规则后才纳入；未确认前不是通过条件 |
| 正式 VFX | P2 候选 | 对技能运行事实的正式特效呈现 | 用户确认所需事实、资源和视觉标准，并有运行证据后验收；占位反馈不视作正式效果 |

P0 建立“基础状态 + 一个完整技能”的可运行表现主流程；P1 验证该主流程能保留技能差异并处理终态；P2 不阻塞试点的 P0/P1 通过。

## 4. 玩家可观察要求

### 4.1 基础行动/待机（P0）

1. 角色静止时呈现稳定待机；开始移动、改变方向、跳跃、下落、落地时能观察到与当前运动事实一致的动作变化。
2. 状态进入/离开应与真实角色状态一致。动作本身不得制造跳跃、落地或移动已经发生的假象。
3. 基础表现和技能动作职责分离。技能动作退出后应接续角色当时真实的基础状态，不应无条件回到 Idle。
4. 默认可控角色是首要验收对象。训练假人、额外角色和未列状态不自动进入 P0 范围。
5. 每种状态的进入/离开事实、玩家输入、可见结果和未覆盖边界应能配对记录；只看资产或状态图不构成体验通过。

### 4.2 技能发起、动作与效果反馈（P0/P1）

1. 有效施法进入 `Started`/前摇后才出现相应施法动作或已确认的降级反馈。请求被拒绝不能播放会误导玩家认为技能已经开始的动作。
2. 动作开始、技能释放、命中/未命中、效果应用和施法完成必须可区分。施法完成不代表命中或效果成功。
3. 表现读取真实运行事件；动画帧、Notify 或特效不能产生技能业务结果。需要动作时点与释放事件配合时，表现结果须和真实释放事实一致。
4. 每次技能动作绑定其施法身份。迟到或重复的前次施法事件不得停止、覆盖或重置当前新动作。
5. 与命中、治疗、持续伤害、附着或移除关联的可见反馈，不能早于对应运行事实。当前占位反馈可作为观察手段，但正式 VFX 需求待定。
6. 动作缺失/不可用、无表现实例或播放失败不得改变技能运行结果；降级反馈不得伪造施法、命中、治疗、伤害或效果成功。最低反馈形态待用户确认。

### 4.3 技能个体差异（火球 P0，其余 P1）

| 技能 | 玩家应理解的事实 | 错误表现判定 |
| --- | --- | --- |
| 火球 | 敌方单位为目标；施法动作与投射物结果相关；命中和未命中结果可区分 | 仅凭动作完成显示命中，或无命中却显示命中效果 |
| 区域爆发 | 目标是地面位置和范围；范围结果来自该次运行事实 | 空区域显示成命中，或反馈目标位置/范围与运行事实不符 |
| 修复 | 效果作用于施法者自身；治疗是否生效和数值以运行结果为准 | 仅动作结束就让玩家认为治疗生效 |
| 燃烧 | 施法动作、持续效果附着、周期伤害和移除是不同过程 | 动作结束时提前结束持续反馈，或无附着/周期结果仍表现为已生效 |

表中“玩家应理解”规定必须传达的业务区别，不规定特定颜色、造型、动画或特效资产。

### 4.4 取消、完成和恢复（P1）

1. 前摇取消、阻塞/死亡取消、超时取消、释放后取消与正常完成均应结束对应动作，并按已确认体验恢复基础表现或呈现收招。
2. 取消与完成不应被误读为命中/未命中；具体取消提示样式待定。释放后取消不撤销已发生的效果事实。
3. 新施法开始后，旧施法的取消、完成或播放清理不得影响新动作。
4. 角色动作恢复不能清理或伪装持续效果。持续效果依据附着、周期伤害和移除事实单独表现。
5. 退出施法动作后应观察到正确的基础状态衔接；动作资源缺失或异常也须有不改变业务结果的恢复路径。

## 5. 资源需求

本试点没有经基线证据支持的新增正式资源需求。可使用以下已记录的资源类别作为核对对象或候选，不得据此认定最终采用：

| 类别 | 已有依据 | 需求边界 |
| --- | --- | --- |
| 角色 Mesh/Skeleton、基础动画 | 共享基线记录 `SK_Mannequin`、Manny/Quinn、Idle/Walk/Jog/Jump 等资源存在 | 核对目标角色绑定、兼容和运行视觉；不承诺其已适用于全部状态 |
| 技能动作 | 共享基线记录四项技能动作软路径和一个正式 Montage 样本 | 可用于试点候选；不指定 Sequence/Montage、Slot、Section、Notify、释放帧或时长 |
| 占位世界/屏幕反馈 | 技能基线记录范围标记、目标标记、结果数值和持续状态反馈 | 只用于运行事实可观察性；不作为正式 VFX/音频/美术交付 |
| 受击、正式 VFX、音频 | 共享基线没有确认具体资源或资源绑定 | 暂无必须新增的资源承诺；需先确认体验选择并核对可用资源 |

发现所需资源不存在或不兼容时，记录为待补资源/待决选择，不自行创造正式资源需求或虚构资源状态。

## 6. 验收条件

文档、资产路径、脚本可读、工具校验或历史日志均不能单独证明玩家视觉通过。每项验收应记录目标运行入口、输入/场景、技能/施法身份、相关运行事实、可见动作/反馈、结果和未覆盖项；历史证据须标明没有本轮复现。

| ID | 阶段 | 通过条件 |
| --- | --- | --- |
| CP01 | P0 基础状态 | 默认可控角色中 Idle/Move/Jump/Fall/Land 可复现；状态事实、进入/离开和视口表现相符，未达成项明示 |
| CP02 | P0 职责边界 | 基础状态、技能动作和结果反馈可分别观察；动画/脚本不决定技能命中、效果、扣费或终态 |
| CP03 | P0 火球 | 同一施法身份可串联开始、动作、真实释放、命中/未命中和终态；可见反馈符合运行结果 |
| CP04 | P1 区域爆发 | 地面目标/范围和实际命中结果相符；空范围不呈现命中成功 |
| CP05 | P1 修复 | 自身目标、治疗应用和动作/结果有明确区别；实际治疗数值来自技能运行结果 |
| CP06 | P1 燃烧 | 附着、DamageTick、BuffRemoved 与动作终态能分别观察；动作结束不提前终止持续效果 |
| CP07 | P1 取消与恢复 | 前摇取消、释放后取消、正常完成、新旧连续施法均不误清理；角色恢复到真实基础状态或已确认收招 |
| CP08 | P1 降级行为 | 无动作资源或资源不可用时，技能业务结果不变；玩家反馈不伪造开始、命中或效果，并可定位内容缺口 |
| CP09 | 边界保留 | UE 执行动画求值/骨骼融合；Lua 试点没有重写引擎动画能力或技能业务规则 |
| CP10 | P2 候选 | 受击和正式 VFX 只有在对应体验选择与资源确认后逐项验收；未确认时标为范围外/未决，不作为 P0/P1 通过阻塞项 |

CP01-CP03 构成 P0 通过门槛；CP04-CP09 构成 P1 通过门槛。P2 不阻塞 P0/P1，但做了就必须按 CP10 及经确认的逐项需求验收。

## 7. 明确排除项

- 全游戏脚本迁移，以及把 Lua 设为全部项目逻辑的默认实现方式。
- 移除所有 C++、Blueprint、Montage、Animation Blueprint 或其他 UE 资产。
- 插件选择、UE 接入、接口、C++ 适配、脚本目录、数据格式、调用方式、具体代码搬迁和运行时架构设计。
- GAS 重写或修改技能目标、命中、伤害、治疗、持续效果、扣费、冷却、前摇/生效/收招、取消/完成语义。
- 用脚本替代 UE 动画求值、姿势混合、骨骼融合或动画压缩。
- 未经确认的动作资源、释放帧、时长、Notify/Slot 命名、VFX/音频/镜头、颜色造型和正式美术质量标准。
- Agent 数量、程序任务拆分和技术验证计划。

## 8. 待用户确认的体验问题

1. 受击表现是否属于本轮试点？若属于，它能否打断技能动作，受到多次命中时如何取舍，何时恢复？
2. 技能取消和完成后，玩家希望角色立即回到基础动作还是保留收招？前摇取消与释放后取消是否需要不同视觉结果？
3. 动作资源缺失或播放失败时，最低可接受的玩家反馈是什么？是否需要显式提示异常，还是仅提供不误导的普通反馈？
4. 四项技能是否都要求正式 VFX？如果是，哪些事实分别需要表现：目标选定、投射物、范围、命中、治疗、持续效果附着、周期伤害和效果移除？
5. 燃烧动作收尾时，玩家是否接受角色已回到基础动作而目标身上的持续效果仍继续显示？持续效果结束是否需要单独的结束反馈？
6. 基础移动之外是否需要本批额外基础状态（例如死亡）？当前共享基线只确认 Idle/Move/Jump/Fall/Land，未据此扩展范围。

## 9. 交给程序侧 PM 核实的技术问题

以下是交接问题，不是策划对技术方案的回答：

1. 当前运行链可向表现侧稳定提供哪些施法身份、阶段、目标、释放、命中/效果、取消和完成事实？事实从哪里产生、哪些已有验证证据可复用？
2. Lua 表现逻辑与 UE 动画系统、Blueprint、现有 C++ 职责和保留资产之间，哪些边界必须在试点内明确？
3. 如何确保旧施法迟到事件、重复事件、动作播放失败或脚本异常不会清理/覆盖新施法，同时保留可定位的观察证据？
4. 现有基础状态、技能动作关联、内容读写入口和占位反馈分别能否复用；哪些仅有实现记录但未有可复现的运行或视觉证据？
5. 目标 UE 版本和正式运行入口如何支持对事件、动作、结果、取消、恢复、持续效果及缺失资源的并行观察？
6. 如何让脚本表现内容可被读取、局部修改、回读和校验，并与人类维护的表现语义一致？
7. 在正式 VFX、受击资源或技能动作缺失时，当前运行链可提供怎样的不误导反馈与内容问题定位？
