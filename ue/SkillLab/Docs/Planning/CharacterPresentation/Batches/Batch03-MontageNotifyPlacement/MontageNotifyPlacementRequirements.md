# AI 技能动作 Notify 配置需求

## 1. 目标与来源

本需求依据 2026-10-27 用户在角色表现策划对话中的确认修订。目标是建立技能配置所需的完整能力：AI 根据技能事件需求和给定动作，自主观察、理解动作阶段并确定 Notify 时点，完成游戏实际使用内容的配置与接入，再通过回读和游戏内观察确认事件与动作对齐。

使用者不需要逐个指定 Notify 的帧号，也不需要把逐点人工检查作为正常配置的必经步骤。玩家释放技能时，发射、攻击等事件与对应动作应具有符合技能意图的时间关系。

本批不再限定为一个 Montage、一个 Notify 或一个样本验证。具体技能配置需要多少动作、多少事件，就应按其实际内容需求处理；验收样例用于证明功能，不替代完整能力要求。本文不要求一次性配置全项目所有技能或清点所有资产。

本需求交给程序侧建设所需能力，并供后续内容配置者使用。本轮只修改策划文档和向总控交接，不启动代码、资产或内容配置。

## 2. 范围与职责

### 功能范围

- 接收技能事件的含义、次数、顺序和约束，以及需要配置的动作。
- 为 AI 提供足以判断动作时点的信息，支持其自主定位事件点位。
- 通过适合 AI 读取和修改的入口维护点位及事件关联，完成实际运行接入。
- 支持多个事件的完整配置、修改后的重新配置、真实结果回读和游戏内验证。
- 反馈资源不足、语义冲突、定位歧义、配置失败和运行偏差。

### 职责边界

策划规定产品行为、能力需求和验收结果。程序侧核实当前事实，决定必要的代码、配置和资产配套修改；本文不选定 C++、GAS、Blueprint、Lua、最终数据载体、资产内部拓扑或程序拆分。

专用 Skill / Agent 是否建立、由谁派发、各对话的上下文和编排顺序，以及怎样高效读取动作，由用户与总控另行讨论。用户提出“设计、表现找资源并确定 Notify、再配置逻辑”作为讨论候选，尚未冻结。本文以下输入输出关系表达内容依赖，不规定 Agent 执行先后。

动作及其他美术资源的寻找、选择、制作流程不在本文定案；本功能需要取得可用动作信息。角色基础状态全面改造、受击或正式 VFX 制作、无关技能重设计和整体表现回归不在本批范围。

## 3. 配置所需输入与产物

### 所需输入

每项配置应能取得：

- 技能希望发生的行为及事件语义，例如一次投射物发射、若干次攻击时机或纯表现提示；业务事件的次数、顺序及限制来自技能需求。
- 已给定或已确认用于该内容的动作，以及能识别动作阶段的观察信息。
- 已明确的动作时点要求和时间约束。若需求只规定“推出手掌时发射”，应由 AI 判断对应帧位；用户无需预先给帧号或手工标注所有参照。
- 该内容适用的运行与失效规则、可用验证入口，以及已约定的时序容差；未提供的必要信息应列明。

业务事件含义和动作帧位是不同输入。不能因为逻辑尚未配置完成，就假定无法描述事件需求；也不能为了先放 Notify，擅自创造新的攻击次数或效果规则。纯表现通知是否需要配置，依据该技能的表现需求判断。

### 交付产物

每项结果应包含技能与动作的对应关系、事件语义及次数、所选时点或适用区间、动作判断依据、实际写入并读回的配置、游戏内观察结论，以及未解决项。具体标识、格式和载体由程序侧设计。

上述产物需要足以供后续配置、运行与复查使用，不能只有一份建议帧号清单。示例事件是语义说明，不指定实际标签、现有资产或现有接口。

## 4. 自主定位与完整配置行为

### 动作判断

AI 应根据可观察的姿势、运动和动作阶段，为每个事件找出符合其含义的时点，并说明依据。例如发射事件可以对应明确的出手动作，攻击事件可以对应需求指定的攻击阶段；实际参照须结合技能意图和给定动作判断。

用户没有提供精确动作参照时，AI 应先利用已有技能含义与动作信息作判断。语义和证据充分时，自主完成正常配置；存在影响结果的歧义时，才请求补充或选择，不把每个帧位都交回用户批准。

### 多事件与动作约束

同一技能涉及多个事件或多个动作时，应逐项对应，满足规定的次数、顺序及相互关系。不能把单个点位放准视为整项配置完成。若内容要求持续窗口，还应明确开始、结束与中断后的关闭语义；是否采用 Notify State 等形式由程序侧决定。

若技能需要三次攻击，但动作只支持一次清晰的挥击，或已有固定时限与可见出手时机冲突，应报告具体冲突及受影响事件。AI 不得静默减少事件、改变效果、移动已确定的业务时限或替换动作。需要修改技能或资源要求时，由相应需求负责人决定。

### 写入与修改

应把点位和事件关联配置到游戏真正使用的内容，并能够在重新加载后回读。用户要求提供便于 AI 修改的入口，减少逐个进入 Montage 编辑器手工操作；入口可涉及配套代码或配置能力，但本文不预先指定实现。

再次配置同一内容时，应能修正目标点位或关联，避免遗留旧结果造成重复触发，并保留与本任务无关的有效事件。动作或事件需求改变后，应重新判断受影响位置，不沿用已经失去依据的帧位。

## 5. 给程序侧的能力需求

| 能力 | 要求的结果 |
| --- | --- |
| 动作信息可用 | AI 能获得与实际使用动作对应、足以识别目标阶段的信息，并将判断位置对应到实际播放时间。高效读取方式尚待讨论。 |
| 事件与动作对应 | 可以表达技能所需事件及其与动作的对应，满足多事件的次数、顺序和适用时段要求。 |
| 便于 AI 修改 | 提供 AI 可读取、修改和检查的入口，减少逐点手工编辑 Montage 的操作；不能只把手工操作说明交回用户。 |
| 配置实际生效 | 支持点位、事件关联及必要运行接入的配套修改，最终被正式运行入口使用。 |
| 回读与更新 | 能重新读取真实生效内容，确认事件、动作、位置和关联；修改后能确认旧配置是否已被替换，避免重复或遗漏。 |
| 业务边界与失效处理 | Notify 发出的执行请求由技能逻辑核验并处理；无效施法或旧施法的通知不能让已失效行为重新执行。 |
| 可观察与可复查 | 能将动作依据、实际配置和游戏内事件关系对应起来，区分定位、写入、关联和运行的问题。 |

程序侧需评估现有能力的复用和缺口，提出必要的配套修改。不能因为现有工具不便于写 Notify，就把本需求缩减为输出建议帧位或要求用户逐点操作。当前是否具备这些能力，均待核实。

## 6. Notify 与技能业务的关系

本次确认的职责划分是：Notify 可以提供“此时请求执行某个技能行为”的时间信号；技能逻辑负责是否允许执行、执行什么及实际结果。

以发射为例，技能需求规定发射含义和约束，AI 将时点对齐给定动作；播放到该时点时可请求技能逻辑发射。Notify 到达不等于必然命中、造成伤害、扣费成功或技能完成。纯表现事件则仅执行其对应表现职责，不制造技能业务事实。

取消、打断或其他已经使施法失效的情形发生后，迟到或旧施法的 Notify 不得重新执行失效业务或影响新施法。已由技能系统确认的效果不能因表现故障被伪造或抹除。具体取消许可、扣费时机、超时与退款规则仍沿用该技能经确认的需求，本文不新增其细则。

动作无法读取、配置不完整或事件没有接入时，生产结果必须报告未完成，不能宣称成功；运行时通知缺失、播放中断等情况的具体终态与降级方式，需要结合技能规则补充，不能默认为已经释放或已经产生效果。

### 与共享基线的衔接

复用现有基线的业务权威、施法身份隔离和证据边界。本次新增的是 AI 自主配置动作事件、便于 AI 修改的入口，以及 Notify 可向技能逻辑提供执行请求的需求。

基线中“表现消费真实事实、不能自行宣告业务结果”的约束继续有效；其中“只消费”等措辞与本次执行请求方向的衔接，需要总控协调澄清并按职责维护。本文记录本次需求增量，不改写共享基线，不宣称现有 Notify 已能驱动技能，也不以动画通知取代技能逻辑对业务许可和结果的裁定。

## 7. 不确定性与失败处理

- 事件含义、次数或顺序缺失：指出缺少的业务信息，取得确认后再配置受影响部分；不凭动作擅自发明技能规则。
- 动作不可读、动作依据不足或有多个不能消解的候选：保留候选及影响，说明需补充什么；不得用任意位置伪装成确定判断。
- 技能与动作要求冲突：提交冲突，等待相应需求负责人取舍；不静默更改已经确定的约束。
- 写入失败、回读不一致、事件未关联或运行入口不使用该结果：标明失败位置和未完成范围，不以工具返回成功代替交付。
- 游戏内时序不符：记录提前或延后方向、偏差和观察条件；在既定需求允许范围内修正后重新验证，不能通过事后放宽容差宣称通过。

配置可以区分已完成和未完成的内容，但受影响技能存在关键缺项时，不能将整个技能标记为可交付。正常明确内容应由 AI 自主处理，人工介入集中于业务取舍和无法自行消解的问题。

## 8. 验收要求与场景

### 判定依据

每项内容验收应对应四类证据：事件意图、动作判断依据、从实际生效内容读回的配置、游戏内动作与事件的时间关系。记录技能与动作、运行入口、观察条件、期望关系、实测偏差和结论，供其他 Review 者复查。

容差应结合事件语义、动作和可观察条件，在评判结果前明确；本文不臆定通用帧数或毫秒数。允许自动判断帧位，不等于允许缺少准确性标准。具体数值尚未确定的内容可以进行能力核查，但不能宣称其时序验收已通过。

### 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 自主判断与配置 | 给出技能事件需求和可观察动作，AI 自主找出对应时点、说明依据并完成实际配置，用户无需逐点指定或确认帧号。 |
| 多事件配置 | 按内容需要配置多个事件，逐项核对次数、顺序和动作关系，无遗漏、额外业务事件或混淆。 |
| 真实结果回读 | 配置保存并重新加载后，从实际运行所用内容读回动作、语义、点位和关联；能识别写入未生效或读错目标。 |
| 游戏内对齐 | 在实际释放入口观察动作及事件，相关发射、攻击或表现提示按需求发生，与目标动作关系符合事先约定的容差。 |
| 修改与重新配置 | 修改事件要求或替换动作后，重新判断并更新受影响内容，读回及运行均无旧结果遗留导致的重复或错位。 |
| 歧义与动作冲突 | 对无法判断或无法承载事件需求的动作明确报告问题，不任意放点、不静默修改技能规则，也不把未完成内容报告为通过。 |
| 取消与施法隔离 | 在该技能允许取消或失效的时机复现相应情形，相关迟到或旧通知不恢复失效业务、不影响新施法。 |
| 缺失与失败可见 | 动作不可读、写入失败、关联缺失或运行未触发时，能区分失败范围并报告；通知到达本身不被记录为命中或成功。 |

单纯结构校验、工具返回成功、配置中存在 Notify、静态位置截图或日志记录，都不能单独证明功能通过。无法开展游戏内观察时，必须标明尚未验收的范围。具体验收内容集合由后续配置任务确定，应覆盖实际使用的事件类型和上述适用场景。

## 9. 程序侧待核实项

- 当前动作与 Montage 的实际使用入口，以及可供 AI 观察的信息和时间对应关系；高效读取方案需要与总控后续讨论衔接。
- 当前 Notify 的真实用途、事件关联及触发方式，哪些只做表现，哪些已经向技能逻辑请求执行；现有权限、许可核验和失效处理是否满足需求。
- 当前可用的 AI 读取、修改、保存和回读能力，实际生效内容能否被核对；为减少手工编辑，需要增加哪些配套能力。
- 当前多事件、动作更新、重复配置及旧结果清理的能力和缺口。
- 正式游戏入口能否观察事件与动作时序，如何区分动画位置、通知触发和实际业务处理的偏差；目前有哪些证据缺口。
- 通知缺失、播放中断或通知迟到时，现有业务终态与内容需求是否一致；不一致之处须提交确认，不能静默改变技能规则。

这些是程序需核实的事实与能力问题，不是策划对现有代码、资产、接口或运行效果的判断。程序架构、实现方式和任务分配由程序侧按其职责形成。

## 10. 已确定与待确认

### 已确定

- 本次是 AI 自主配置技能动作 Notify 的完整功能需求，已取消原单样本验证限制。
- 根据事件需求和给定动作自主判断时点，完成实际配置、接入、回读和游戏内验证，减少用户逐点检查。
- 提供适合 AI 修改的入口，可以需要配套程序修改，具体技术不在策划定案。
- Notify 提供时机请求，技能逻辑负责业务许可与结果；工作流编排不由本策划对话决定。

### 待总控与用户讨论

- 专用 Skill / Agent、派发者、上下文、设计与资源及逻辑配置之间的编排和反馈。
- AI 如何高效、可靠地读取动作，相关能力由谁准备、如何验证足以支持判断。
- 本次事件请求需求与现有共享基线的措辞衔接和维护责任。

### 随具体内容补充

- 实际技能、动作和所需事件清单，特定时限和时序容差。
- 不能同时满足技能与动作要求时的内容取舍。
- 现行技能规则未覆盖的通知缺失或中断处理。此类关键规则未明确时，相应内容不能视为完成。

尚未冻结 Agent 顺序、具体技术方案或动作读取方法。尚未核实当前程序能力，尚未产生本功能的配置与游戏内验收证据。
