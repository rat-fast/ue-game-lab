# 00：动画基础数据与状态

## 目的

降低动画核心计算和状态判断对 Animation Blueprint Event Graph 的依赖，同时保持角色基础动作行为可逐步比较和回归。

## 当前共享基线依赖

共享表现基线列出了 Idle/Walk/Jog/Jump 等资产存在，但未证明它们已绑定到默认角色或在运行中正确切换；因此下列内容均是本批目标，不是现状描述。

## 本批策划承诺

- 动画基础数据计算应迁出 Animation Blueprint Event Graph 中的核心判断逻辑。Event Graph 不应继续成为主要的项目级核心计算规则承载处。
- 基础动作状态按可验证的小步整理，覆盖 Idle、Move、Jump、Fall、Land。Move 可包含当前角色移动表现所需的移动变化，但具体参数、混合规则与状态组织由程序架构评估。
- 每次状态或切换逻辑迁移，都应能在明确运行入口和相同输入条件下与迁移前表现比较；在迁移前记录对照行为和已知差异。
- 姿势求值、骨骼融合和引擎动画求值仍由 UE 执行。本需求改变项目逻辑的组织和生产接口，不改造底层引擎能力。

## 建议实现方向

将数据采集/计算、状态语义与动画资源组织分开表达，并让人和机器可以定位各自职责。具体是由 C++、配置、Data Asset、Blueprint 或组合承载，不在策划侧定案；不要求逐节点复制 Event Graph。

## 当前限制

- 当前没有默认角色状态机、AnimBP 绑定、状态输入来源和运动覆盖范围的可复现验证记录。
- 现有基础动画资产存在不证明全部状态都有合适资源或适合当前 Skeleton。

## 验收条件

- 能指出原 Event Graph 中承担核心计算/判断的职责及迁移后对应入口；常规状态变化不再依赖图内分散的核心判断。
- Idle、Move、Jump、Fall、Land 均有明确的进入/离开条件、输入事实和实际运行表现；未覆盖或不可达的状态被显式报告。
- 逐步迁移记录能够在相同场景和输入下比较改造前后的可观察结果，并说明允许差异和缺陷。
- 默认可控角色的状态变化可在 UE 运行入口中复现；只凭图结构或资产文件存在不通过。

## 明确排除项

不规定状态机拓扑、BlendSpace、AnimBP 节点、类名、变量名或动画参数的最终编码形式；不重写 UE 的姿势求值或动画压缩。
