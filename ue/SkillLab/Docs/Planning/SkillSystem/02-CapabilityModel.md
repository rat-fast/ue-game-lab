# 技能系统能力模型与系统分层（草稿）

## 文档定位

本文档是第二层的总览，用于把第一层总体目标转换为共同的领域地图。详细流程、配置和默认行为分别写入模块稿；模块地图、阅读顺序与开工条件见 [索引](README.md)。第一份样例见 [M01 输入与技能装配](02-Modules/M01-InputAndSkillLoadout.md)。模块稿描述设计，尚不代表实现完成。

本文档当前不决定：

- 最终 C++ 类名和目录；
- GAS 是否承载每个概念的全部职责；
- 最终配置格式、DataAsset、DataTable、DSL 或脚本形态；
- 每个效果的最终数值和全部例外规则。

本文档要先回答：

- 系统中有哪些稳定概念；
- 这些概念之间如何产生、依赖和结束；
- 哪些是稳定运行能力，哪些是可变内容，哪些是运行时状态；
- GAS、SkillLab 项目模块、表现和验证分别应关注什么。

## 二、核心概念

### 1. 输入动作、技能槽位与技能装配

输入动作是对玩家设备输入的逻辑解释，例如“激活槽位 1”。按键绑定把 Q 等物理按键映射到输入动作，动作再指向槽位。AI 和测试工具可以直接提交请求，不必模拟按键。技能装配表示角色当前具备哪些技能及其槽位分配；拥有的技能不一定都放在快捷栏上。

三者需要分开：

```text
物理按键：Q
输入动作：激活槽位 1
技能槽位：第 1 格
技能装配：第 1 格当前装配 Fireball
```

这样可以在不修改技能定义的情况下更换角色的技能装配，也可以在测试时通过 UI 或受控数据入口快速替换槽位内容。

首版提供最简单的运行中试用入口：点击槽位 → 从可用技能列表选择技能 → 更新装配 → 使用对应按键试放。显示当前技能、冷却和不可用原因。战斗中的替换限制、旧技能运行中处理和保存策略由 M01 给出建议默认值，相关生命周期规则与 M02/M03 对齐；不要求每次换技能手改配置。

### 2. 目标预览与确认

目标预览是在技能正式提交前显示范围、方向、落点或候选目标的状态。目标确认表示玩家点击、松开按键、确认界面操作或 AI 完成选择后，形成可提交的目标解析结果。

瞬发技能、AI 和测试工具可以跳过预览，但技能系统仍应能接收已经确认的单位、位置、方向或其他目标上下文。

### 3. 战斗单位

战斗单位是可以拥有属性、状态和能力，并参与目标选择与效果结算的运行时对象。

它至少需要表达：

- 稳定身份；
- 阵营或关系类别；
- 属性和资源；
- 当前状态；
- 能力集合；
- 死亡、重置和清理生命周期。

战斗单位不等于当前的 `Character`。未来可能由 Character、Pawn、独立组件或其他 Actor 组合提供。能力模型只规定它必须具备的领域能力，不提前规定唯一 UE 类归属。

### 4. 阵营与关系

阵营用于表达施法者与目标之间的关系，并参与目标过滤、效果合法性和表现识别。

首版至少需要区分：

- 自身；
- 友方；
- 敌方；
- 中立或无关系目标。

阵营关系不应散落在每个技能的专用判断中，而应成为目标查询和效果规则可以共同读取的概念。

### 5. 属性与资源

属性是可被效果修改、被技能读取或参与条件判断的数值概念。

资源是技能激活和持续执行可能消耗的属性类别，例如生命、法力、能量或其他项目资源。当前不规定首版最终资源种类，但要求资源能够进入能力激活、效果结算和重置语义。

需要区分：

- 基础值；
- 当前值；
- 最大值；
- 派生值；
- 属性修改来源；
- 初始化和重置状态。

### 6. 状态

状态是单位在一段时间内具有的、会影响能力、目标或表现的运行时事实。

状态可以来自效果，也可以作为能力门控条件被读取。死亡、眩晕、沉默、施法中、不可选中和免疫都属于状态语义候选。

状态与效果需要区分：

- 效果描述一次修改或施加行为；
- 状态描述修改产生后仍然成立的条件。

### 7. 技能定义

技能定义是可重复使用的内容描述，表达一个技能能够做什么以及如何组合已有运行能力。

它可能包含：

- 激活条件；
- 资源和冷却参数；
- 目标类型；
- 时间线参数；
- 命中方式；
- 效果组合；
- 表现事件引用；
- 允许的取消和中断行为。

技能定义不是一次施法。它是内容层对象，可以被多个单位装配或由多个运行实例读取。

### 8. 操作意图

操作意图是玩家、AI 或测试工具希望达成的动作目标。它回答的是“想做什么”，不保证已经对应到一次具体的能力调用。它首先是解释概念，不要求每个入口创建独立 Intent 对象；简单按键和测试入口可以直接形成请求。

例如：

- 使用火球攻击鼠标指向的敌人；
- 对一个友方单位施放治疗；
- 在指定地面位置释放范围技能；
- 向当前移动方向发起冲刺。

意图可以来自不同入口，也可以比最终施法请求更抽象。AI 的意图可能是“攻击最近的敌人”，需要经过技能选择和目标解析后，才能形成具体请求。

### 9. 施法请求

施法请求是根据操作意图整理出的、向技能系统提交一次具体能力调用尝试的统一入口。

它至少需要携带：

- 请求来源；
- 施法者；
- 能力标识；
- 目标解析结果；
- 必要的方向、位置或单位引用；
- 请求时间或上下文；
- 取消或替换信息（如果适用）。

施法请求不是激活成功的保证。系统仍需执行能力条件、资源、冷却、状态和目标合法性检查。

意图和请求的区别是：

```text
意图：我想用火球攻击鼠标指向的敌人
请求：请玩家单位尝试激活 Fireball，目标为 Enemy_03，方向为 Y
```

同一个意图可以产生多个请求；一个请求被拒绝，也不代表原始意图已经消失。

### 10. 请求缓冲与命令队列

请求缓冲是指技能系统在当前不能立即执行时，暂时保留一次输入或施法请求。例如角色正在闪避，玩家提前按下普攻，系统可以选择在闪避结束后尝试执行，或直接丢弃。

它不是所有技能都必须具备的默认行为。第二层只记录它作为可选的调用链能力，具体规则需要决定：

- 哪些技能允许缓冲；
- 缓冲持续多久；
- 新请求是否覆盖旧请求；
- 角色死亡、受控或状态变化时是否清空；
- 何时重试、何时过期并报告结果。重新执行前必须走普通激活检查，不能以已缓冲为理由绕过门控。

单次输入缓冲可以只保存最近一个待执行动作，不等于按顺序保存多个动作的命令队列。普通按键事件和 Enhanced Input 触发器不会自动提供“闪避结束后补出普攻”的玩法缓冲。是否保留输入、何时重试和何时过期属于操作体验规则；容器与对象实现由程序线决定。

### 11. 施法上下文

施法上下文是一次技能运行从前置调用链带入执行阶段的信息集合。它可以包含：

- 施法者；
- 技能定义或能力标识；
- 目标解析结果；
- 施法位置和方向；
- 请求来源；
- 激活时的属性、标签或其他快照；
- 施法实例标识。

施法上下文用于让投射物、范围、持续区域和效果知道这次运行来自哪里，但不要求后续执行结果必须与前置目标完全一致。执行阶段仍可按照技能规则重新查询目标并产生不同的实际命中结果。

### 12. 施法实例

施法实例是一次具体能力运行的生命周期对象。

它用于关联：

- 一次激活尝试；
- 施法者和能力定义；
- 施法上下文中的目标信息与实际命中；
- 当前阶段；
- 创建的效果、投射物、区域、监听和计时器；
- 取消、打断、结束和失败原因；
- 表现事件与日志。

施法实例是技能定义和运行时对象之间的重要连接，不能只用一个“技能是否在冷却”的布尔值代替。

### 13. 目标解析、目标查询与命中事件

前置目标解析、目标查询与命中事件需要分开：

- **目标解析结果**：经过输入、意图和预览/确认后形成的单位、位置、方向或其他目标上下文；
- **目标查询**：根据技能规则、阵营、距离、范围、视线和碰撞找到候选目标；
- **命中事件**：执行过程中实际产生的命中结果，可发生在释放、投射物碰撞、范围查询或周期检查时。

鼠标选中的对象不一定是合法施法目标，合法施法目标也不一定在最终命中时仍然有效。

### 14. 效果

效果是技能、物品或其他运行原因对目标产生的可观察改变。

首版需要能够表达：

- 瞬时效果；
- 持续效果；
- 周期效果；
- 属性修改；
- 伤害、治疗和护盾；
- 增益、减益和控制；
- 状态施加、移除和驱散。

效果应能追踪施法者、目标、来源技能和应用时间，以支持规则判断、日志和调试。

### 15. 临时运行时对象

投射物、持续区域、引导对象、监听器和计时器是能力执行过程中产生的临时对象。

它们需要有明确的：

- 创建者；
- 所属施法实例；
- 持续时间；
- 命中或结束条件；
- 施法者取消、死亡和重置时的处理；
- 销毁和残留检查方式。

### 16. 表现事件与 UI 状态

表现事件把运行语义传递给动画、特效、音频和 UI。

候选事件包括：

- 技能预览；
- 激活成功或失败；
- 前摇开始；
- 释放或生成投射物；
- 命中；
- 效果施加或移除；
- 引导开始、中断和结束；
- 冷却开始和结束；
- 技能完成或失败。

表现事件描述发生了什么，不直接替代表现资源本身。

UI 读取装配、冷却、资源、瞄准和不可用原因等状态，并提交换装或施法操作；技能结果由运行逻辑决定。表现、UI 和日志可以在每个阶段接收通知，不是等待效果结算后才开始工作。

## 三、概念之间的基本生命周期

```text
技能定义 + 施法请求
        ↓
激活条件与目标合法性检查
        ↓
创建施法实例
        ↓
前摇 / 释放 / 引导 / 投射物或区域执行
        ↓
目标查询与命中事件
        ↓
效果应用与状态变化
        ↓
表现事件、日志和结果
        ↓
结束、取消、打断或重置清理
```

这条链描述一次成功施放的示意。失败尝试是否分配实例、实例如何映射到 GAS 对象，由程序线选择；策划只要求区分“未开始就被拒绝”和“已经开始后中断”。能力结束也不等于投射物或持续效果立即结束。资源扣除、冷却、目标锁定和后续对象存续规则分别由 M03、M04、M06 细化；共享约定集中维护。图中表现与日志可发生于各阶段，并非只在结算后产生。

## 四、从输入到效果的运行链路

第二层需要明确不同入口如何汇入同一套技能运行能力。完整链路可以先表示为：

```text
输入信号
    ↓
操作意图
    ↓
目标、位置或方向解析
    ↓
施法请求
    ↓
激活条件与目标合法性检查
    ↓
施法实例
    ↓
前摇 / 释放 / 引导 / 投射物 / 范围 / 持续区域
    ↓
命中事件
    ↓
效果结算与状态变化
    ↓
表现事件、日志和结果
```

### 输入信号

输入信号是设备或外部系统产生的事实，例如按键、鼠标点击、鼠标位置、方向输入或测试命令。它属于输入层，不等于技能语义。

### 操作意图

操作意图表达希望达成的动作目标，例如“攻击某个敌人”或“在该位置施放范围技能”。玩家、AI 和测试工具可以用不同方式产生意图。

### 目标、位置或方向解析

系统将意图中的抽象目标转换成技能请求所需的具体单位引用、地面位置、方向或其他目标上下文。这一步可以包含预览、选择、替换和取消。

### 施法请求

施法请求是一次可被技能系统接受或拒绝的具体调用。它应包含能力标识、施法者、目标上下文和请求来源，但不代表能力一定开始运行。

### 激活判定

系统检查能力是否存在、是否冷却、资源是否足够、施法者是否被状态阻塞，以及请求目标是否满足技能条件。是否以及何时分配运行对象交给程序线；本层只区分请求拒绝与已开始的施放。

### 施法实例与执行

施法实例记录这一次具体运行的阶段、目标、临时对象、效果、表现事件和结束原因。它可以执行前摇、投射物、范围、引导、多段生效或持续区域。

### 命中、效果与结果

命中事件表示执行过程中实际找到或碰撞到的目标；效果结算则决定对目标产生什么属性变化、状态变化或其他结果。命中和效果都可能再次失败，例如目标已经死亡、离开范围或获得免疫。

### 各入口的共同边界

```text
玩家输入 → 槽位解析 → 可选的瞄准与确认 ─┐
AI 决策 → 技能与目标选择 ────────────┼→ 施法请求 → 可选缓冲 → 激活判定 → 执行
测试工具 → 指定技能与目标 ───────────┘
```

玩家、AI 和测试工具不要求共享输入层和意图生成方式，但从施法请求开始，应尽量共享同一套激活、执行、效果、表现、日志和清理语义。

本节只定义概念和链路。资源扣除、目标锁定、失败重试、命中重检或取消清理的默认规则进入对应第二层模块，跨模块约定集中维护。意图是解释概念，不要求各入口分配独立对象；表现和日志可以订阅每个阶段。

## 五、系统分层

### A. 稳定运行能力

负责重复执行且应保持一致的能力：

- 能力激活和生命周期；
- 属性和效果修改；
- 标签查询和状态门控；
- 目标查询和过滤；
- 范围、方向、碰撞和投射物执行；
- 持续区域和周期处理；
- 取消、打断、清理和重置；
- 日志和调试。

### B. 可变技能内容

负责通过数据或受控内容入口变化的部分：

- 技能参数；
- 资源和冷却值；
- 目标类型；
- 时间线参数；
- 命中形状参数；
- 效果组合；
- 状态持续时间和强度；
- 表现资源引用；
- 角色的能力装配。

### C. 运行时状态

负责表达当前世界正在发生什么：

- 当前属性和资源；
- 当前能力阶段；
- 当前冷却和阻塞状态；
- 当前施法实例；
- 活跃效果和状态；
- 存在中的投射物和区域；
- 当前目标和命中记录。

### D. 表现与资源连接

负责把运行事件连接到动画、Niagara、音频、UI、图标和挂点，但不重新决定技能规则。

### E. 验证与观测

负责让人和 AI 能够读取、复现、检查和回滚技能运行：

- 施法阶段和失败原因；
- 目标与命中记录；
- 效果和状态变化；
- 临时对象清理；
- 重置结果；
- 配置校验和能力缺口报告。

## 六、GAS 与项目能力的概念映射草案

| 概念层 | GAS 可能承载 | SkillLab 需要补充或定义 |
|---|---|---|
| 能力 | `GameplayAbility`、能力授予和激活 | 统一施法请求、项目激活语义和内容装配 |
| 能力系统状态 | `AbilitySystemComponent` | 单位所有权、初始化、重置和与项目单位的连接 |
| 属性 | `AttributeSet`、属性修改 | 属性分类、资源解释、初始化来源和重置 |
| 效果 | `GameplayEffect` | 伤害、治疗、护盾、控制、驱散等项目语义 |
| 状态 | `GameplayTag`、持续效果 | 标签命名、状态关系、免疫、冲突和表现解释 |
| 目标与命中 | Effect Context 可记录结果 | 目标解析结果、查询、空间检测、投射物和持续区域 |
| 表现 | `GameplayCue` | 事件契约、资源连接、缺失资源处理和调试反馈 |
| 验证 | GAS 可调用和可观察的运行机制 | 日志、重置、回归、样本和生产接口 |

这不是最终程序结构，也不代表 GAS 必须直接实现所有项目语义。它只是用于识别需要继续验证的职责边界。

## 七、传统项目组与 AI Native 项目组的职责

### 传统项目组

通常由多个岗位共同完成：

- 系统/战斗策划：定义技能、效果、目标和状态的业务含义；
- 技术策划：整理参数、对象关系和可实现规则；
- Gameplay 程序：把稳定能力映射到 GAS、C++、组件和 UE 运行时；
- 技术美术或表现程序：定义事件到动画、特效和音频的连接；
- QA/战斗测试：发现规则缺口、回归问题和不可复现状态。

第二层文档的价值，是把这些岗位分散掌握的稳定概念、关系和边界集中表达出来。

### AI Native 项目组

AI Native 不意味着增加一个“策划 Agent”替代所有岗位，而是让人、AI 和工具围绕共同的领域模型协作：

| 参与者 | 在第二层中的主要职责 |
|---|---|
| 人类负责人 | 确认目标、范围、取舍、专业语义和最终责任；处理冲突与未决问题。 |
| AI | 提取概念候选、整理关系、生成映射草案、检查遗漏、维护来源和影响分析。 |
| 程序与工具 | 验证模型能否落到稳定运行能力，提供结构校验、生成、加载、日志、重置和回滚。 |
| 表现参与者 | 检查表现事件是否足以表达运行语义，识别资源和时序缺口。 |

人类仍然负责“系统应该表达什么”和“什么结果算正确”；AI 更适合承担概念整理、候选生成、跨文档一致性检查和重复维护；工具负责确定性执行和硬校验。
