# Batch01 输入、操作意图与技能请求链路

## 文档定位

本文定义第一批技能从玩家输入到统一技能请求的业务链路。它只规定输入如何形成操作意图、如何捕获技能身份、如何生成目标上下文和请求，不规定输入组件、Widget、GAS 类、C++ 文件或数据载体。

AI、测试和玩家可以有不同的输入来源，但从“提交技能请求”开始必须进入同一条技能运行链路。本文中的 `SkillId`、`RequestId`、`CastId`、目标规格和事件阶段沿用程序线当前的公共语义；它们是交接概念，不是策划要求的字段实现。

## 一、业务链路

```text
物理输入
  → 逻辑动作
  → 交互状态更新
  → 槽位解析
  → 捕获 SkillId
  → 形成操作意图
  → 目标预览/合法性提示
  → 确认或取消
  → 生成统一技能请求
  → 激活与施法生命周期
```

### 1. 物理输入

物理输入是按键、鼠标按钮、鼠标移动、指针点击、失焦和测试调用等原始事件。它只表达“发生了什么输入”，不直接表达技能效果、目标命中、资源扣除或冷却结果。

### 2. 逻辑动作

逻辑动作是输入系统对原始事件的业务解释。Batch01 至少需要能够表达：

| 逻辑动作                                  | 业务意义                   |
| ------------------------------------- | ---------------------- |
| `ActivateSlot`                        | 请求使用某个技能槽位             |
| `ConfirmTarget`                       | 确认当前操作意图中的目标上下文        |
| `CancelIntent`                        | 取消尚未提交的操作意图            |
| `BeginHold` / `EndHold`               | 开始/结束需要持续输入的会话         |
| `UpdateAim`                           | 更新鼠标、位置或方向带来的瞄准上下文     |
| `MoveCommand`                         | 提交移动意图；是否取消前台施法由施法规则决定 |
| `FocusLost` / `ControlledUnitChanged` | 清理当前未提交交互状态            |

逻辑动作不能直接应用伤害、治疗、护盾或状态，也不能绕过统一技能请求。

### 3. 交互状态

输入层至少区分以下状态：

- `Idle`：没有正在选择或瞄准的技能；
- `LoadoutSelection`：正在查看或修改槽位装配；
- `IntentPreview`：已选择技能，正在形成或更新操作意图；
- `Committed`：操作意图已生成请求，输入层等待请求结果；
- `HeldSession`：已开始或正在维持需要持续输入的技能会话。

交互状态不等于施法阶段。技能已经开始后，输入层只负责继续发送维持、停止或取消动作，不能通过重新读取当前槽位改变已经捕获的技能身份。

### 4. 槽位解析与技能身份捕获

`ActivateSlot` 首先读取该时刻的槽位装配结果：

1. 槽位为空，返回可见的空槽结果，不创建技能请求；
2. 槽位有技能，捕获当时的 `SkillId` 和可选的装配快照；
3. 根据技能的输入/目标需求决定直接请求，还是进入 `IntentPreview`；
4. 后续换装不能把已经捕获的操作意图、待提交请求或已开始施法重定向到另一技能。

槽位是“当前位置装配了什么技能”，不是技能定义、能力授予或施法实例。换装不能刷新原技能冷却，也不能修改已经开始对象的归属。

### 5. 操作意图

操作意图是玩家准备执行某个技能的业务意图，至少包含：

- 来源（Player、AI 或 Test）；
- 施法单位；
- 已捕获的 `SkillId`；
- 输入模式（直接、单位目标、地面位置、方向或持续会话）；
- 当前目标上下文（单位、位置、方向或 Self）；
- 当前预览状态和取消原因（若有）；
- 需要持续输入时的会话身份。

操作意图可以无效、可以被取消，也可以在确认时因目标变化而无法提交。它不代表已激活、不代表已扣费，也不代表已经命中。

### 6. 预览与确认

- 预览只显示当前目标上下文的候选合法性、形状或方向，不产生正式效果；
- 预览使用的目标、位置和方向是待确认快照，提交和施法阶段仍要重新检查；
- `ConfirmTarget` 将当前操作意图转换为统一技能请求；
- `CancelIntent`、失焦、切换被控单位、槽位替换或目标上下文失效会清理未提交意图；
- 预览中右键单击、UI 点击、右键拖动等冲突由当前项目输入规则分流，不能让一次物理输入同时确认技能和移动/镜头。

### 7. 统一技能请求

请求提交至少表达：来源、施法单位、捕获的 `SkillId`、目标规格、请求追踪身份以及可选的装配快照。程序可以用不同载体承载这些语义。

请求提交后由技能生命周期统一检查：单位是否有效、技能是否可用/已授予、状态是否允许、资源与冷却是否满足、目标是否仍合法。输入层不执行这些检查的替代版本。

请求结果至少能区分：

- 尚未开始的 `Rejected`；
- 已开始并获得 `CastId` 的 `Started`；
- 已开始后的 `Cancelled`、`Interrupted` 或正常 `Completed`；
- 效果应用是否成功及其实际结果。

请求被拒绝时，输入层保留可读原因，但不把它伪装成施法失败后的效果事件。预览取消也不创建正式请求终态。

## 二、输入与技能配置的边界

| 内容                                     | 类型     | 归属            |
| -------------------------------------- | ------ | ------------- |
| Q/W/E/R 或其他按键绑定                        | 可配置内容  | 输入/装配配置       |
| 技能需要单位、地面、方向还是持续输入                     | 技能配置语义 | 技能内容文档        |
| 点击确认、按住确认、松开停止的操作规则                    | 技能配置语义 | 技能内容文档与公共输入能力 |
| 预览取消不产生正式效果                            | 固定业务规则 | 基建能力          |
| 当前槽位、已捕获 SkillId、当前预览目标                | 运行时状态  | 输入/意图运行对象     |
| 如何存储绑定、如何接入 Enhanced Input、如何组织 Widget | 技术实现   | 程序线           |

按键不是技能本身。技能文档声明所需的输入意图类型，输入系统负责把物理事件形成该意图；技能生命周期负责判断请求能否开始。

## 三、交接验收

1. 按槽位键能够得到该时刻的 `SkillId`；换装后新输入得到新技能，旧意图/旧施法不被改写。
2. 单位、地面和方向技能都能形成预览；预览取消不产生正式技能请求或效果。
3. 预览确认形成统一请求；请求拒绝时没有资源、冷却、Cast 或效果副作用。
4. 需要持续输入的技能能够开始、维持和停止同一个会话；松开、失焦、换装不会误调用当前槽位的新技能。
5. UI 点击、右键单击取消、右键拖动镜头和移动命令不会被一次输入重复消费。
6. Player、AI、Test 可以绕过物理按键，但提交后使用相同的请求和施法语义。
