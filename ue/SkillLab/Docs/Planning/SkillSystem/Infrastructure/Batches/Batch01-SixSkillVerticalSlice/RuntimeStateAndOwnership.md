# Batch01 运行时状态与所有权

## 文档定位

本文说明 Batch01 中哪些内容是固定业务规则、哪些来自技能配置、哪些是运行时状态，以及每类状态由哪类运行能力拥有。它用于防止技能内容、输入层、施法生命周期和效果层互相写入对方状态。

## 一、四类内容

| 类别 | 定义 | Batch01 例子 |
|---|---|---|
| 固定业务规则 | 所有技能都必须遵守的公共不变量 | 请求拒绝无正式副作用；成功开始后才有施法实例；终态和清理幂等；来源可追踪 |
| 技能配置 | 每个技能可以声明的业务参数和选择 | 输入模式、目标关系、成本、冷却、阶段时长、空间尺寸、效果强度、叠加/移除策略 |
| 运行时状态 | 运行过程中产生、变化和终结的事实 | 当前装配、操作意图、目标快照、请求、施法阶段、冷却剩余、对象位置、效果剩余时间 |
| 程序实现 | 为实现上述语义而采用的技术方式 | GAS 类、C++ 组件、Blueprint、数据载体、序列化、计时和对象存储 |

策划案只能确定前两类和运行时状态的业务含义；不把程序实现方式写成硬性要求。

## 二、当前程序线可复用的语义

以下名称来自现有程序文档和实现切片，用来保持策划与程序交接语言一致。策划不要求它们必须成为最终字段或类名：

| 语义身份/事实 | 业务含义 |
|---|---|
| `UnitId` | 本轮运行中稳定识别一个施法者或目标单位 |
| `SkillId` | 可复用技能内容的身份，不代表一次施法 |
| `GrantedAbilityId` | 单位当前获得某技能调用资格的身份 |
| `RequestId` | 一次提交尝试，包括被拒绝的请求 |
| `CastId` | 一次已经开始的技能运行 |
| `EffectApplicationId` | 一次效果应用或持续效果的可追踪身份 |
| `TargetSpec` | Self、单位、位置或方向等目标语义 |
| `Source` | Player、AI 或 Test 等调用来源 |
| `EffectResult` | 效果是否应用、实际数值、失败/免疫等结果 |
| `EventType` / `Stage` | 运行事实和所处阶段的可观察事件 |

## 三、所有权边界

| 状态            | 拥有者        | 其他层可以做什么                     |
| ------------- | ---------- | ---------------------------- |
| 当前槽位装配        | 输入/装配层     | 查询、提交装配变更；不能改变已开始施法          |
| 操作意图和预览       | 输入/目标交互层   | 更新、确认、取消；不能直接施加效果            |
| 请求结果          | 请求入口/生命周期层 | 读取状态和原因；不能伪造成功               |
| 施法阶段、支付、冷却、终态 | 施法生命周期层    | 接收取消/停止/死亡/Reset；不能由 UI 直接改写 |
| 目标解析与去重       | 目标/空间层     | 提供候选和过滤结果；不能拥有效果状态           |
| 投射物/区域等执行对象   | 执行载体层      | 按来源请求终止或查询；不能因换装改变归属         |
| 生命、资源、效果、状态   | 属性效果层      | 应用、刷新、移除、报告实际结果；不能自行选择目标     |
| 预览、动画、UI、日志   | 反馈/观测层     | 订阅事实和显示；不能决定命中或扣费            |

## 四、固定业务不变量

1. 预览和操作意图不是正式施法；取消预览不产生正式效果。
2. 请求被拒绝时不创建已开始施法，不扣正式资源，不启动技能冷却，不产生正式效果。
3. `CastId` 只属于已开始运行；槽位替换、技能定义变化或 UI 状态变化不能改写已有 `CastId`。
4. 效果结果必须区分候选命中、效果应用成功、免疫、目标失效和实际数值为零。
5. 每个运行事实由拥有者产生一次；反馈和日志只能转发、显示或保存，不能重新推断另一套状态。
6. 取消、打断、死亡、销毁和 Reset 都必须有明确终止原因；重复清理不得重复扣费、命中、应用效果或发布终态。
7. Reset 必须覆盖本单位拥有的输入状态、施法、对象、冷却和效果，以及由本单位施加到其他单位的持续状态。

## 五、技能配置不得越界的内容

技能可以配置目标、输入意图、阶段、资源、冷却、空间、效果和表现选择；不能配置或绕过：

- 请求是否跳过激活检查；
- 是否在拒绝时产生正式效果；
- 是否伪造 `Started`、命中或效果成功；
- 是否把另一个槽位或技能改写为当前施法身份；
- 是否跳过来源、施法、效果和清理追踪；
- 是否由表现资源决定逻辑命中。

## 六、程序交接结果

程序线需要根据本文和现有架构文档给出：

- 可供技能侧调用的请求、目标、效果、对象和反馈能力；
- 每项能力接受的业务输入、返回的业务结果和失败原因；
- 当前已经存在的能力、需要扩展的能力和仍属程序内部的能力；
- 若实现方式改变，如何保持上述固定业务不变量。

这些是程序接口交接要求，不是策划对 GAS 类、C++ 类或资产结构的指定。
