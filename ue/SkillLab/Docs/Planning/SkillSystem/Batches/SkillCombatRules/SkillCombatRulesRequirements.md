# 技能战斗规则框架策划案

状态：核心操作策略已由用户确认（2026-11-05）；多 Cast 共同仲裁规则于 2026-11-12 确认，详见第 8.2 节，实施与验证状态不得由需求确认推定。普通/重击通过权威事件 Gameplay Tag 分类。Tag 命名与当前伤害入口的接线由程序核实并实现；受击来源尚无现成 Runtime 事件。其他通用能力按本案要求。

## 1. 目标和边界

建立覆盖 SkillLab 当前技能系统的可复用技能战斗规则框架，让策划能表达技能时序、操作限制、触发与状态效果，并让玩家获得一致、可理解的响应。增加同类技能应主要复用已有规则和内容配置；修改共同规则应能集中完成，技能差异不要求为每项编写公共机制专属分支。

方案需结合现有项目和实际技能需求，核实可复用的 GAS 与项目能力，形成能够持续承载技能时序、操作仲裁、状态效果和清理的通用框架。通用适用范围不以示例技能为上限，也不把抽象数量或代码层数作为完成标准；新增规则应优先复用统一入口、状态管理和清理契约。

通用框架涵盖 Ability 生命周期与技能时序关系、玩家输入和能力激活仲裁、移动/取消/打断/衔接规则、Tag 与事件语义、状态效果所有权、运行结果及清理。现有四技能可用于对照，不构成适用范围上限；闪避、沉默、硬直和多段技能是能力讨论示例，不代表已有内容或要求本次新增这些技能/Buff。

与原技能链路改造分开：沿用 GAS Ability 激活及施法生命周期、动画 Cast Notify 经带 Tag 的 Gameplay Event 通知当前 Ability 推进释放、权威运行层产生实际效果等基线语义。本案提出原任务排除的操作规则，不改变或重新定义其交付范围；原基线和既有功能应保持，必要变更及兼容差异经确认。

## 2. 技能时序与阶段

前摇、生效、后摇及取消窗口是项目战斗规则中的概念，不是 GAS 强制规定的阶段；如何对应 Ability 生命周期由程序架构结合现状确定。每个技能必须有明确的生效、效果提交和结束行为，以及适用的操作规则；不要求每个技能都具有前摇或后摇，也不要求每项各填写前后摇时长。前摇是技能的准备过程，后摇是技能或动作的收尾过程；其起止与效果提交、判定点的关系由具体技能定义，不预设前摇结束即提交效果。动画收尾是否限制操作由规则决定，不能仅凭阶段名称推导。

### 2.1 时序如何定义、技能如何填写

每个技能都要有一份可被运行层识别的**时序意图**，但不必把所有阶段都填写成一套固定表格。最少需要说明：何时算正式受理、有哪些效果提交点、每个提交点由什么有效事实触发、提交后何时结束，以及各时机采用哪些操作规则。技能没有前摇时，明确声明激活后即可进入第一个提交点；技能没有后摇时，提交完成即可结束。前摇、判定点、命中和结算可以分别存在，也可以由同一时点承担。

为了让常见技能主要依靠配置复用，内容侧应能选择共享的时序模式，例如即时提交、等待释放点后提交、多个提交点及提交后仍有收尾。模式只提供可复用的时序骨架，不替技能决定受击、取消、衔接和资源结果；技能只补充提交点、目标/效果关系和必要的差异策略。运行层负责把这些声明绑定到当前施法身份、事件等待和清理流程。Lua 可以封装和推进时序组合，但不能在公共运行状态之外另存一套独立决定施法结果的状态。

因此，前摇和后摇的配置要求是“是否存在以及如何影响操作”，不是“每项必须填一个时长”。若某技能依赖动画长度、Notify 或其他有效条件，内容需声明该触发关系；若只需要逻辑时序而没有对应表现，仍需声明可验证的提交条件和终态。具体字段、脚本形式和动画资产制作方式由程序/表现侧确定。

框架应能表达并组合：激活即提交、等待动画释放点或其他有效条件、一个或多个效果提交点、效果在提交后异步命中或持续、提交后收尾，以及无需前摇或后摇的技能。不同技能可复用时序模式并声明必要差异；前摇结束、提交、实际命中和效果结算是不同事实，不要求彼此必然同一时刻。多次提交各自的触发、目标和次数由技能内容定义，不能重复触发。

动画 Notify 表达对应语义时点；Ability 按技能定义及当前施法身份推进，Notify 本身不证明命中、伤害或治疗。动画时点、内容配置和运行状态应有明确权威来源，不要求重复维护同一时点。通知超时、中断和重复提交按第 8 节处理；迟到通知不得影响新施法。具体接线与既有内容的兼容情况由程序侧核实，不根据表现推断补发或退款。

## 3. 规则组合与操作仲裁

通用规则应能读取适用的技能/Ability 类别、当前时机或窗口、角色状态、输入意图及事件语义，并给出允许、拒绝、等待/缓存、取消或继续等明确结果。阶段名称本身不隐含某一结果；受击打断、主动取消和允许衔接的动作分别作为规则选择配置，由公共逻辑解释。一个技能选择既有规则并按内容声明差异；规则应能在多技能间复用，同一技能也可按时机选择不同规则。通用机制执行规则结果，内容不能绕过激活校验或权威结算。

多个 Cast 同时存在时，所有尚未结束且仍拥有操作限制的施法共同约束新技能请求，不能只采用最新激活技能的规则。全部允许后仍需通过正式门控；有明确拒绝则拒绝，只有需要等待且适用规则允许缓存时才使用角色级单槽 latest-wins 缓存。缓存重评估、闪避取消范围和独立效果边界按第 8.2 节执行。

框架需具备下列表达能力；本案已确认的默认操作规则见第 8 节，技能可以在公共契约允许的范围内声明差异：

- **激活与衔接**：根据当前技能及请求类别决定新请求能否激活，支持互斥、允许衔接、取消当前后激活等明确结果；不得把允许激活自动解释为并行或取消。
- **移动与主动取消**：可区分移动输入被允许、被拒绝或使技能取消，以及取消窗口是否开放；输入不等于角色已移动，取消不等于效果从未提交。
- **受击与控制**：区分瞬时受击事件、攻击类别/强度和持续控制状态；支持技能及其时机采用不同打断策略。阻止新 Ability 激活与打断已运行 Ability 是独立规则。
- **输入缓存与后摇接招**：可表达是否接收、何时消费、何时失效以及终止时如何处理；缓存不等于请求已受理或一定成功。容量、替换、清槽和共同仲裁按第 8 节执行；本案不额外规定按时长过期的缓存规则。
- **规则冲突与原因**：当状态限制、技能策略和新输入同时适用时，必须能得到确定结果和可观察原因；优先顺序和例外授权以第 8 节及其共同仲裁规则为准，不由 Tag 名称或实现顺序暗中决定。

此前以前摇期间普通技能、闪避和受击为例讨论规则组合；具体默认操作规则已由第 8 节确定，多 Cast 请求仲裁由第 8.2 节确定。不同技能仍可按已确认的配置能力选择共享规则与必要差异，不以示例或阶段名称替代实际规则判断。

## 4. Tag、事件与效果语义

Tag 是共享的分类和条件语义，不自行执行操作。项目应维护可审阅的语义及校验方式，明确层级、适用对象和匹配语义，避免同义或互相矛盾的标签。Tag 的语义由公共规则和统一注册/校验入口解释，技能内容引用这些语义，不应在每个技能里重新发明“沉默是什么”或“重击是什么”。以下是类别示意，并非最终命名：

| 语义类别 | 表达 | 关键边界 |
| --- | --- | --- |
| 状态 | 角色当前沉默、硬直等 | 持续事实须有明确来源和失效条件；不能直接推断具体规则结果 |
| 事件 | 释放点、受击等瞬时事实 | 事件可携带来源、目标及必要强度等上下文；不等于持续状态或实际效果 |
| Ability/技能类别 | 普通技能、闪避等分类 | 分类不等于角色当前正在执行；规则决定该类别是否受限制 |
| 效果类别及数据语义 | 治疗、伤害、持续效果和相关数值含义 | 效果实际生效及数值由权威结算决定，Tag 不代替效果实例或数值 |

Tag、事件和 Buff/GameplayEffect 需要区分：Tag 是可匹配的名称或分类；事件 Tag 描述一次瞬时事实，状态 Tag 描述某个有效状态或资格，Ability 类别 Tag 描述技能分类。Buff/GameplayEffect 是带有来源、持续/周期、叠加或移除事实的运行效果，它可以授予或撤销状态 Tag，但 Tag 本身没有持续时间、周期、层数或属性修改。因而“拥有沉默状态”可以由有效效果授予 `State.Control.Silence`，规则再消费该状态；“这次受到重击”则是带 `Event.Hit.Heavy` 的瞬时事件，不能被当作一个持续 Buff。具体标签名和效果载体仍由程序侧结合项目现状落定。

状态可由效果等合法来源授予。应区分状态来源与目标是否拥有状态：多个有效来源产生同一状态时，一个来源结束不应清除其他来源仍维持的状态；状态最终移除应能恢复相应规则判断。Buff/GameplayEffect 的持续期、周期、叠加、刷新、免疫等具体玩法不可仅由 Tag 推定，未确认的效果规则另行决定。状态产生、移除及订阅有明确管理者；Ability 结束不应误清仍独立生效的持续效果。

## 5. 内容表达与公共机制

默认方向：GAS 负责 Ability 生命周期、属性和效果等基础能力；C++ 优先承载公共执行机制和通用战斗规则；Lua 负责具体技能配置、规则选择、参数及需要的特殊流程；高频可调纯数值按现有方向使用 JSON。参数可由技能内容引用数值来源，不要求同一参数在 Lua 和 JSON 重复维护。语言分工不是硬性教条，具体规则及载体由程序架构结合实际修改、调试、接口和校验成本决定。

这里的“C++ 公共机制”不是把每个技能写成固定分支，而是提供一组稳定、可组合的能力契约。策划案对职责的预期如下，具体类名和 API 不在本案中规定：

| 能力层 | 应提供的公共能力 | 内容/脚本侧可以选择或组合的内容 |
| --- | --- | --- |
| 运行身份与生命周期 | 为请求、Cast、提交点和事件建立可区分身份；推进受理、运行、完成、取消、打断、失败和 Reset；拒绝旧事件影响新运行 | 技能采用的时序模式、提交点数量和特殊流程分支 |
| 正式门控与共同仲裁 | 统一检查角色状态、资格、资源、冷却、目标和所有仍有效 Cast 的操作限制；产生允许、拒绝、等待/缓存及原因 | 技能类别、规则引用、哪些窗口允许等待/缓存、必要的差异授权 |
| 时序与事件等待 | 维护有效窗口、Notify/Gameplay Event 等触发、超时和一次性提交；保证提交幂等并在结束时清理 | 即时提交、Notify 提交、多提交点、提交后收尾、取消窗口及各提交点的目标/效果关系 |
| Tag 与状态查询 | 统一注册、层级匹配、事件上下文传递和状态来源查询；不因匹配 Tag 自动执行效果 | 引用 `Ability.Category`、`State.Control`、`Event.Hit` 等公共语义，选择适用规则 |
| 效果、资源与所有权 | 通过 GAS/权威运行层产生属性变化、Buff、投射物等结果，处理计费/冷却、来源和清理边界 | 目标关系、效果组合、参数来源、持续效果是否独立于 Cast |
| 诊断与表现事实 | 输出阶段/窗口、运行身份、匹配规则、拒绝/打断原因、提交和清理事实 | 技能和表现消费哪些事实；不自行伪造受理、命中或效果 |

Lua 可以封装“选择和组合公共能力”，例如把某个技能声明为“等待释放点提交、前摇受重击打断、允许闪避、Recovery 禁止普通技能、命中后施加持续效果”。脚本推进流程时应调用公共行为入口，不另行维护一套权威施法状态，也不绕过公共门控直接扣资源、授予状态或宣布命中。新增一种公共语义（例如新的打断类别、共同仲裁方式或新的提交保证）应先明确其公共规则契约，再由内容引用，避免在各技能中重复定义。若某个特殊流程只由少数技能使用，也可由脚本编排已公开的公共操作，由程序侧评估是否应上升为共享能力。

内容侧应能声明技能类别、时序模式、释放/效果事件关系、适用的共享操作规则和必要差异；规则应具有明确的触发条件与结果，不以技能 ID 散落在公共流程中。共享规则的实现和每个技能选用的规则分开；Tag 语义有统一入口，同一状态有明确管理者，同一规则不在多层重复权威判断。不同语言或数据载体可以参与同一条链路，但对外必须表现为同一套规则入口和同一套清理责任。

公共运行机制需支持读取有效上下文、判断及执行请求结果、识别当前 Ability/施法、处理事件及效果提交、维护相应时机与窗口、提供终态和拒绝原因、清理本次运行拥有的等待、检测、窗口与临时状态。脚本接口应封装完整行为及其清理责任；技能结束、取消或失败时，公共层应清理该次执行持有的任务、检测与窗口等资源。脚本/内容不能绕过公共流程伪造受理、命中、效果或终态。具体接口、节点模型和复用方式由程序架构确定，不能以固定三阶段或 Lua 全权控制推断实现。

**公共规则实现与技能选用分开**：以沉默为例，公共规则解释“有效沉默状态如何限制新激活、如何作用于运行中的 Cast”，Buff 负责按其来源和持续规则维持状态，技能内容引用适用规则。以受击打断为例，公共规则读取权威事件类别和当前有效策略，技能选择普通/重击是否打断、在哪些窗口生效。第 8 节确认的是本案默认策略，不应因此把 `Windup`、`Recovery` 或某个状态 Tag 写成不可组合的技能专属分支。

**语言归属的调整依据**：公共规则可以在 C++ 中以可配置方式执行，也可以由 Lua 统一封装后经公共入口执行。调整依据是修改频率、调试成本、跨层接口成本和能否保持统一判断及清理，不以“策划规则必须全在 Lua”或“通用规则必须全写成 C++ 固定分支”作决定。高频纯数值沿用现有 JSON 方向；本案不另立配置语言或万能规则编辑器。

## 6. 终止、清理与可观察性

完成、主动取消、受击打断、死亡、目标失效、Reset 及执行失败须产生可区分结果。对应运行结束时清理该次施法拥有的事件等待、计时、检测、窗口、临时状态及按规则需要清除的输入；已提交结果和独立持续效果依据其自身规则保留，不能因动作终止伪造回滚。旧事件、重复事件或迟到通知不得推进或取消新的施法，终态和效果提交不得重复。

框架应让程序与验证人员能观察当前技能、运行身份、时机/窗口、相关状态、规则匹配与拒绝/打断原因，以及效果是否已提交；表现只能消费已产生的真实事实。可观察内容用于验证和定位，不要求本案新增 UI 或规定日志格式。

## 7. 验收场景

以下为能力验收场景；规则判定以第 8 节为准。第三列记录本次程序证据边界，不把未有生产内容或未运行的场景记为通过。详细命令和日志见[程序实现摘要](../../../../ProgramWorkflow/SkillSystem/Batches/SkillCombatRules/Implementation/CombatRulesImplementationSummary.md)。

| 场景 | 预期能力或通过条件 | 本次程序证据 |
| --- | --- | --- |
| 时序多样性 | 内容可表达即时提交、等待 Notify、多个提交点及可选收尾；不因缺少固定前后摇而无法运行，不重复提交 | 部分：现有 GameplayEvent 释放路径通过；Cast 内身份提交点幂等单测通过；无多提交内容定义或可配置时序窗口，仍为固定阶段模型 |

### 8.1 提交结果不确定：策划定案

本节依据用户授权的策划判断确定 `SkillCombatRulesCompletion` 提交异常产品语义；它补充第 8 节而不改变已确认的首次成功提交计费规则。**提交成功**指权威运行机制确认该提交点已成功接受并产生应有的提交事实，不等同于后续投射物命中、实际伤害或治疗。`Indeterminate` 指提交已发起但当前无法确认是否成功，既不是明确失败，也不是成功；不由动画、脚本返回或超时推断效果已发生。

**正常路径**：首次成功提交确定一次能量费用和一次冷却；同一 Cast 后续成功提交不再次扣费或重启冷却。提交前取消或明确失败且从未成功提交，不扣能量、不启动本 Cast 冷却。已成功提交的效果及费用不因后续取消、失败或表现异常回滚。提交点重复事件不重复执行或计费。

**首次提交结果不确定**：当尚未有成功提交时，对本次所需能量作临时预留，不当作已扣除；其他请求只能使用未预留的可用能量。冷却尚未正式启动，但同一技能暂不可再次激活，理由为提交结果待确认；其他技能在满足各自条件及可用能量时可正常运行。可观察资源信息须区分实际能量、预留量及可用量，不得显示为已退款或已扣除；在没有专门 UI 时，通过现有结果/诊断通道提供同等事实，不要求新增 UI。

**已计费后发生不确定**：若本 Cast 已有成功提交，保留已有的费用与冷却，不再预留、扣费或启动第二次冷却；不确定的后续提交点不推断成功或失败，已确认成功的其他效果继续有效。

**等待、终态与恢复**：停止该 Cast 的后续提交、该提交点的重复触发和自动重新施放；可等待权威结果，但等待不得无限占用施法或让玩家一直处于施法锁定。采用有限的异常等待窗口，具体时长由程序结合可运行机制确定并可验证；到期后以可区分的“提交结果未确认”异常终态结束 Ability/Cast、释放本次施法的动画/输入锁和可清理运行资源。终态不宣称效果成功或失败，缓存输入按异常终止清除；仍未解决的结算隔离独立于已结束的 Cast。等待期间若收到权威结果可提前结束等待并按实际结果收敛。不得把线程永久卡死、进程失去执行能力等情况描述为保证可由计时器自动恢复。

**权威结果收敛**：若后续确认首次提交成功，将预留结转为一次正式费用并启动一次冷却；冷却从权威可确定的首次成功提交时刻起算，若该时刻不可获得则从确认成功时起算，不重新执行效果。若权威确认所有尚不确定的首次提交均未成功，释放预留且不启动本 Cast 冷却；只有曾实际扣除且能确认属于该次未成功提交的临时扣款，才可原路恢复一次，不能覆盖其他能量变化。若确认结果仍不明，不得凭超时、取消或推测退款、扣费、补发效果或重试同一提交点。已计费 Cast 的后续提交即使确认失败，也不退此前成功提交的费用或重置冷却。各确认及通知须去重，迟到结果只能关联原提交身份，不能影响新 Cast。

**重试与通知**：等待或异常终态后未确认期间，同技能新请求明确拒绝并给出“上次提交结果未确认”；禁止自动重复提交及玩家触发的同技能重新施放，避免重复效果。最终确认后解除该隔离，玩家的新请求重新经过资源、冷却、目标及状态门控，不能复用旧 Cast/提交身份。其他技能仅受实际可用能量及既有门控约束。以现有反馈通道报告“结果待确认/异常结束”，确认后至多一次补充报告实际成功或失败及费用/冷却变化；不得报告虚假的命中、治疗或退款。若接收对象已销毁，保留可诊断结果而不向不存在的对象发送通知。

**Reset 与生命周期边界**：Reset 取消当前 Cast、清除缓存和可清理等待；若有未确认提交，不得因 Reset 单方面认定失败、释放预留或触发重复提交。若同一会话内的角色/ASC 继续存在，未确认记录及隔离须跨 Reset 保留并可继续收敛；Reset 对资源的恢复应以独立的 Reset 语义执行，且不能与预留结转造成重复恢复/扣费。若无法同时保证 Reset 与未确认结算的隔离，Reset 必须明确报告未完成/受阻，不得宣称完整重置成功。EndPlay、Actor 或 ASC 销毁时，取消回调和运行资源，不向失效对象操作；若权威结果仍可由有效所有者处理则继续收敛，否则标记无法在本会话确认并记录原因，不承诺自动退款、结果通知或恢复到不存在的对象。进程退出/崩溃后本任务不承诺持久化、跨进程对账或自动补偿；若无法在退出前确认，保持未确认事实，不伪称结算完成。后续存档/跨会话恢复须另立需求。

**验收**：分别覆盖首次成功、明确失败、首次不确定后成功/失败/始终无法确认、已有成功后另一点不确定、重复与迟到结果、并发其他技能、同技能重试、Reset、EndPlay/对象销毁及进程退出边界。验证实际能量/预留/可用量、冷却起点、结果与通知、异常终态及清理；确认成功最多计费一次，明确失败恢复一次，不确定不伪结算。用可控失联/无回执验证有限等待与未确认隔离；线程完全卡死或进程退出只验证可观察边界，不声称定时恢复。程序须核实如何实现可靠预留、权威确认、结果关联、冷却起点和 Reset 隔离；不能满足时报告具体冲突与证据，不以未知当作失败或静默降级。

### 8.2 多 Cast 共同仲裁：用户确认规则

**确认来源**：用户在程序 PM 对话 `01a1c141-9845-7451-a590-98ca95590f9a` 于 2026-11-12 对“所有仍在施法的技能共同约束”及其配套规则回答“行”（用户消息 `01a1cb94-f01b-73c0-b626-53d23eec495f`），随后要求先将规则写入权威需求，再由程序侧执行（用户消息 `01a1cb96-3cd3-7f63-926a-05d4f1c932ec`）。本节明确第 8 节在多个 Cast 同时存在时的含义，不替代可配置时序及共享/差异化规则能力，不以最新激活的 Cast 作为唯一仲裁者。

**参与范围与激活**：当技能配置允许 A 与 B 同时施法时，A 不因 B 激活而失去约束新请求的能力。所有尚未结束、仍拥有操作限制的施法都参与新请求的共同判断；全部允许后仍需通过角色状态、资源、冷却、目标及其他正式门控。存在明确拒绝则拒绝；没有明确拒绝、只是需要等待且适用规则允许缓存时，使用已有角色级单槽 latest-wins 缓存。等待/缓存不能覆盖另一个 Cast 的明确拒绝，不按施法新旧顺序取代任一仍有效限制。

**缓存重评估**：缓存是角色共用的下一技能意图，不为每个 Cast 新建槽位。相关限制解除后，在安全仲裁点重新检查所有仍有效施法限制及资源、冷却、目标等正式门控。结果仍需等待且允许缓存时继续保留；明确拒绝则拒绝并按已有规则处理缓存，原因可观察；全部允许并通过门控时才以新请求身份尝试激活。单个 Cast 自然结束仅移除它自身的施法限制，不能借此绕过其他 Cast；取消、死亡、Reset 的清槽约定继续有效。

**闪避**：闪避请求先取消所有当前施法，再走正式激活门控；即使闪避激活失败，也不恢复已取消的施法。取消后已成功提交的效果、一次性计费与冷却继续遵循原有规则，第 8.1 节未确认结算的隔离不因取消而被抹除。此处仅明确闪避的全体取消范围，不扩展为普通技能可以无条件取消所有施法。

**独立效果**：已交付并独立运行的投射物、持续 Buff 不因自身仍存在就参与施法接招限制；它们在原施法结束后可按各自既有规则继续运行。它们授予的有效沉默、硬直等控制状态仍由角色状态门控处理，不能据此认为 Buff 无法限制技能激活；闪避取消施法不等于回滚已成功提交的独立效果。

| A 的配置允许 B 激活且 A 继续；之后 A 处于 Recovery/等待限制，B 允许新请求 C | C 不能只凭 B 允许而激活；A 明确拒绝则拒绝，A 只要求等待且适用规则允许缓存则进入角色级单槽缓存 |
| 多个 Cast 对 C 的结果混合为明确拒绝、允许或等待/允许缓存 | 只要有明确拒绝就拒绝，其他允许或缓存结果不能覆盖；无明确拒绝但需等待且适用规则允许缓存时才缓存；全部允许后仍检查正式门控 |
| C 已缓存，某个 Cast 自然结束，但另一个 Cast 的等待限制仍有效且允许缓存 | 只解除已结束 Cast 的限制；C 继续等待，不提前激活；相关限制解除后重新检查全部仍有效限制以及资源、冷却、目标等门控 |
| 等待期间更新下一技能输入，随后相关限制解除 | 仍只有角色级一个 latest-wins 槽位，重评估最新意图；正式门控通过才尝试激活，失败给出原因，不复用旧 Cast/请求身份 |
| A、B 同时施法时请求闪避，分别验证闪避门控通过与失败 | 两种情况都先取消 A、B；通过时尝试正式激活闪避，失败时原 A、B 均不恢复，结果与原因可观察 |
| 原施法已结束，独立投射物或持续 Buff 仍运行，再请求新技能 | 独立效果存续本身不阻止接招；若仍有有效控制状态则依角色状态门控判断。已提交效果不因取消或闪避而回滚 |

本次确认范围内无额外产品待决项。实现接口、当前内容适配和可运行验证方式由程序 PM 核实；本节落盘不表示新规则已实现或验收通过。

## 9. 实现核实与交付关系

**程序/输入映射核实**：当前没有受击事件进入 Runtime。实现需由权威伤害/攻击入口携带事件 Tag，使普通与重击分类明确；不得按伤害数值阈值推断。当前也未发现 Stunned/Silenced 的生产授予方，需确认有效 Gameplay Effect/Tag 来源并在实现/验证交付中标明；若本项目没有相应战斗内容，本案仅能验证正式状态 Tag 有效时的 Runtime 门控行为，不得声称已提供可游玩的硬直/沉默来源。

**实现核实**：按架构交接落实身份安全的显式窗口、通用规则匹配、缓存意图清理、资源/提交幂等、受击 Tag 事件和可观察原因；Tag 本身不自动执行操作，实际结果仍由 Runtime/Ability/GAS 产生。

**交付关系**：已确认规则的 Runtime/GAS 实现、定向自动化和独立 Review 已完成；缓存自然完成后的消费及新请求身份隔离已通过定向复查。受击 Tag 源接线及状态授予者的当前事实仍须报告；生产端到端、可见 PIE 和 Notify 超时独立测试尚未覆盖。本案不修改共享基线或原链路任务。
