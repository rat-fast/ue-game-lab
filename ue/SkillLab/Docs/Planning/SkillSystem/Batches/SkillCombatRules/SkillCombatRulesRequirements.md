# 技能战斗规则框架策划案

状态：核心操作策略已由用户确认（2026-11-05）；普通/重击通过权威事件 Gameplay Tag 分类。Tag 命名与当前伤害入口的接线由程序核实并实现；受击来源尚无现成 Runtime 事件。其他通用能力按本案要求。

## 1. 目标和边界

建立覆盖 SkillLab 当前技能系统的可复用技能战斗规则框架，让策划能表达技能时序、操作限制、触发与状态效果，并让玩家获得一致、可理解的响应。增加同类技能应主要复用已有规则和内容配置；修改共同规则应能集中完成，技能差异不要求为每项编写公共机制专属分支。

方案需结合现有项目和实际技能需求，核实可复用的 GAS 与项目能力，验证新增抽象是否解决当前规则表达、执行或维护问题，避免预设支持所有未来玩法的万能框架。通用适用范围不以示例技能为上限，也不把抽象数量或代码层数作为完成标准。

通用框架涵盖 Ability 生命周期与技能时序关系、玩家输入和能力激活仲裁、移动/取消/打断/衔接规则、Tag 与事件语义、状态效果所有权、运行结果及清理。现有四技能可用于对照，不构成适用范围上限；闪避、沉默、硬直和多段技能是能力讨论示例，不代表已有内容或要求本次新增这些技能/Buff。

与原技能链路改造分开：沿用 GAS Ability 激活及施法生命周期、动画 Cast Notify 经带 Tag 的 Gameplay Event 通知当前 Ability 推进释放、权威运行层产生实际效果等基线语义。本案提出原任务排除的操作规则，不改变或重新定义其交付范围；原基线和既有功能应保持，必要变更及兼容差异经确认。

## 2. 技能时序与阶段

前摇、生效、后摇及取消窗口是项目战斗规则中的概念，不是 GAS 强制规定的阶段；如何对应 Ability 生命周期由程序架构结合现状确定。每个技能必须有明确的生效、效果提交和结束行为，以及适用的操作规则；不要求每个技能都具有前摇或后摇，也不要求每项各填写前后摇时长。前摇是技能的准备过程，后摇是技能或动作的收尾过程；其起止与效果提交、判定点的关系由具体技能定义，不预设前摇结束即提交效果。动画收尾是否限制操作由规则决定，不能仅凭阶段名称推导。

框架应能表达并组合：激活即提交、等待动画释放点或其他有效条件、一个或多个效果提交点、效果在提交后异步命中或持续、提交后收尾，以及无需前摇或后摇的技能。不同技能可复用时序模式并声明必要差异；前摇结束、提交、实际命中和效果结算是不同事实，不要求彼此必然同一时刻。多次提交各自的触发、目标和次数由技能内容定义，不能重复触发。

动画 Notify 表达对应语义时点；Ability 按技能定义及当前施法身份推进，Notify 本身不证明命中、伤害或治疗。动画时点、内容配置和运行状态应有明确权威来源，不要求重复维护同一时点。缺失、中断或迟到通知的具体玩家结果待核实和确认，不在本案虚构自动补发或退款规则。

## 3. 规则组合与操作仲裁

通用规则应能读取适用的技能/Ability 类别、当前时机或窗口、角色状态、输入意图及事件语义，并给出允许、拒绝、等待/缓存、取消或继续等明确结果。阶段名称本身不隐含某一结果；受击打断、主动取消和允许衔接的动作分别作为规则选择配置，由公共逻辑解释。一个技能选择既有规则并按内容声明差异；规则应能在多技能间复用，同一技能也可按时机选择不同规则。通用机制执行规则结果，内容不能绕过激活校验或权威结算。

框架需具备下列表达能力，具体默认值待确认：

- **激活与衔接**：根据当前技能及请求类别决定新请求能否激活，支持互斥、允许衔接、取消当前后激活等明确结果；不得把允许激活自动解释为并行或取消。
- **移动与主动取消**：可区分移动输入被允许、被拒绝或使技能取消，以及取消窗口是否开放；输入不等于角色已移动，取消不等于效果从未提交。
- **受击与控制**：区分瞬时受击事件、攻击类别/强度和持续控制状态；支持技能及其时机采用不同打断策略。阻止新 Ability 激活与打断已运行 Ability 是独立规则。
- **输入缓存与后摇接招**：可表达是否接收、何时消费、何时失效以及终止时如何处理；缓存不等于请求已受理或一定成功。输入容量、替换、过期与冲突优先级待确认。
- **规则冲突与原因**：当状态限制、技能策略和新输入同时适用时，必须能得到确定结果和可观察原因；具体优先顺序、默认规则及例外授权待确认，不由 Tag 名称或实现顺序暗中决定。

示例，供讨论而非已确认：普通技能前摇期间拒绝其他普通技能，可接收闪避请求；受击或重击触发打断。仍需决定闪避是否取消原技能、普通受击和重击是否同等有效、取消后的资源与冷却结果。规则应能表达这些不同选择，不把示例固化为所有技能的规则。

## 4. Tag、事件与效果语义

Tag 是共享的分类和条件语义，不自行执行操作。项目应维护可审阅的语义及校验方式，明确层级、适用对象和匹配语义，避免同义或互相矛盾的标签。以下是类别示意，并非最终命名：

| 语义类别 | 表达 | 关键边界 |
| --- | --- | --- |
| 状态 | 角色当前沉默、硬直等 | 持续事实须有明确来源和失效条件；不能直接推断具体规则结果 |
| 事件 | 释放点、受击等瞬时事实 | 事件可携带来源、目标及必要强度等上下文；不等于持续状态或实际效果 |
| Ability/技能类别 | 普通技能、闪避等分类 | 分类不等于角色当前正在执行；规则决定该类别是否受限制 |
| 效果类别及数据语义 | 治疗、伤害、持续效果和相关数值含义 | 效果实际生效及数值由权威结算决定，Tag 不代替效果实例或数值 |

状态可由效果等合法来源授予。应区分状态来源与目标是否拥有状态：多个有效来源产生同一状态时，一个来源结束不应清除其他来源仍维持的状态；状态最终移除应能恢复相应规则判断。Buff/GameplayEffect 的持续期、周期、叠加、刷新、免疫等具体玩法不可仅由 Tag 推定，未确认的效果规则另行决定。状态产生、移除及订阅有明确管理者；Ability 结束不应误清仍独立生效的持续效果。

## 5. 内容表达与公共机制

默认方向：GAS 负责 Ability 生命周期、属性和效果等基础能力；C++ 优先承载公共执行机制和通用战斗规则；Lua 负责具体技能配置、规则选择、参数及需要的特殊流程；高频可调纯数值按现有方向使用 JSON。参数可由技能内容引用数值来源，不要求同一参数在 Lua 和 JSON 重复维护。语言分工不是硬性教条，具体规则及载体由程序架构结合实际修改、调试、接口和校验成本决定。

内容侧应能声明技能类别、时序模式、释放/效果事件关系、适用的共享操作规则和必要差异；规则应具有明确的触发条件与结果，不以技能 ID 散落在公共流程中。共享规则的实现和每个技能选用的规则分开；Tag 语义有统一入口，同一状态有明确管理者，同一规则不在多层重复权威判断。

公共运行机制需支持读取有效上下文、判断及执行请求结果、识别当前 Ability/施法、处理事件及效果提交、维护相应时机与窗口、提供终态和拒绝原因、清理本次运行拥有的等待、检测、窗口与临时状态。脚本接口应封装完整行为及其清理责任；技能结束、取消或失败时，公共层应清理该次执行持有的任务、检测与窗口等资源。脚本/内容不能绕过公共流程伪造受理、命中、效果或终态。具体接口、节点模型和复用方式由程序架构确定，不能以固定三阶段或 Lua 全权控制推断实现。

## 6. 终止、清理与可观察性

完成、主动取消、受击打断、死亡、目标失效、Reset 及执行失败须产生可区分结果。对应运行结束时清理该次施法拥有的事件等待、计时、检测、窗口、临时状态及按规则需要清除的输入；已提交结果和独立持续效果依据其自身规则保留，不能因动作终止伪造回滚。旧事件、重复事件或迟到通知不得推进或取消新的施法，终态和效果提交不得重复。

框架应让程序与验证人员能观察当前技能、运行身份、时机/窗口、相关状态、规则匹配与拒绝/打断原因，以及效果是否已提交；表现只能消费已产生的真实事实。可观察内容用于验证和定位，不要求本案新增 UI 或规定日志格式。

| 沉默和硬直 | 两类有效状态 Tag 均阻止新激活并打断当前 Cast；状态解除后重试可重新进入正式门控 | Runtime 自动化通过 loose Tag fixture；生产授予者不存在/未发现，不代表可游玩来源 |

## 8. 已确认的产品决策

用户已确认以下通用规则，作为本案实现和验收依据：

| 条件 | 规则 |
| --- | --- |
| Cast 中收到闪避请求 | 取消当前 Cast，然后立即尝试正式激活闪避；激活仍须经过 Runtime/GAS 门控。 |
| 普通受击 / 重击 | 普通受击不打断；重击打断当前 Cast。权威事件通过 Gameplay Tag 标记类别，不按伤害数值阈值推断；实际受击事件生产路径由程序接通。 |
| 沉默 / 硬直 | 阻止新技能激活，并打断当前 Cast。规则消费有效状态 Tag；程序核实并记录现有 Tag 授予来源，缺少生产来源时不得伪称已存在。 |
| 移动 / 主动取消 | 不打断当前技能。地面选点 Escape 仍只取消预览，不作为主动取消技能。 |
| Recovery | Recovery 期间不接新技能。 |
| 输入缓存 | 单槽 latest-wins，只缓存下一技能输入意图；当前 Cast 结束时重新经过正式激活、目标、资源和冷却门控；取消、死亡、Reset 时清除。 |
| Recovery 与缓存消费 | Recovery 期间不激活新请求，但缓存意图可保留。当前 Cast 自然完成并退出 Recovery 后，在旧 Cast/Ability 清理完成的安全仲裁点重新经过 Runtime/GAS 激活、目标、资源和冷却门控；允许时尝试激活，拒绝时报告原因。取消、死亡、Reset 清除缓存。 |
| 费用 / 冷却 | 在效果/释放提交时扣能量并启动冷却；提交前取消不扣，提交后不退款、不回滚已提交效果。 |
| Notify / Ability 中断 | Notify/Gameplay Event 超时或 Ability 中断则取消，不自动补发效果。 |
| 多提交 | 每个已声明提交点在每个 Cast 中最多成功一次；重复事件忽略或拒绝并保持 Cast，不因单次重复自动取消。其他正常完成/取消按生命周期处理。 |

## 9. 实现核实与交付关系

**程序/输入映射核实**：当前没有受击事件进入 Runtime。实现需由权威伤害/攻击入口携带事件 Tag，使普通与重击分类明确；不得按伤害数值阈值推断。当前也未发现 Stunned/Silenced 的生产授予方，需确认有效 Gameplay Effect/Tag 来源并在实现/验证交付中标明；若本项目没有相应战斗内容，本案仅能验证正式状态 Tag 有效时的 Runtime 门控行为，不得声称已提供可游玩的硬直/沉默来源。

**实现核实**：按架构交接落实身份安全的显式窗口、通用规则匹配、缓存意图清理、资源/提交幂等、受击 Tag 事件和可观察原因；Tag 本身不自动执行操作，实际结果仍由 Runtime/Ability/GAS 产生。

**交付关系**：已确认规则的 Runtime/GAS 实现、定向自动化和独立 Review 已完成；缓存自然完成后的消费及新请求身份隔离已通过定向复查。受击 Tag 源接线及状态授予者的当前事实仍须报告；生产端到端、可见 PIE 和 Notify 超时独立测试尚未覆盖。本案不修改共享基线或原链路任务。
