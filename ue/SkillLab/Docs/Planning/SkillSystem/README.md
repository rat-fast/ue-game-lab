## 第二层模块地图

当前按九个职责包组织，编号用于导航，不代表开发顺序或九个 C++ 类。M05、M06 体量较大，确实需要独立阅读时再拆子文档，预计可能发展到约 11～13 份模块文档；这是组织估计，不是工作量承诺。

| 编号与模块 | 覆盖内容 | 主要依赖/交接 | 细化方式 |
|---|---|---|---|
| M01 输入与技能装配 | 按键、槽位、换装 UI、前置交互与请求形成 | M02 能力可用集合；M03 请求；M04 瞄准 | 已有草稿，优先看玩家操作 |
| M02 战斗单位与能力基础 | 身份、阵营、ASC 归属、初始化、授予移除、死亡与重置 | 给所有模块提供单位与能力身份 | AI 先定技术方案，人看死亡与重置行为 |
| M03 技能定义、请求与施法生命周期 | 定义和实例、上下文、激活、提交、资源冷却时点、阶段、中断、缓冲 | M02 单位；M04 目标；M05 资源与状态 | 优先看提交、中断与缓冲体验 |
| M04 目标与命中 | 单位/地面/方向目标、预览数据、过滤、空间查询、命中重检 | M01 交互；M06 执行载体；M05 效果应用 | 优先看瞄准与命中规则 |
| M05 属性、效果与状态 | 属性资源、伤害治疗护盾、持续周期、控制、驱散、免疫、叠加 | M02 单位；M03 提交；M04 命中 | AI 给默认规则，人看战斗结果；必要时拆属性/效果/状态 |
| M06 执行载体与移动 | 直接执行、投射物、范围、持续区域、引导、多段、位移；对象存续 | M03 阶段；M04 查询；M05 效果 | AI 按典型技能起草，人看样本；必要时拆空间载体/位移 |
| M07 表现与 UI 反馈 | 动画、特效、音频、UI 订阅、资源绑定和缺失回退 | 订阅各模块事件，不接管规则 | AI 先定事件接口，人看运行反馈 |
| M08 AI 与测试调用 | AI 的技能目标选择适配、直接请求、换装与批量试放入口 | 调 M01/M02 装配、M03 请求、M04 目标；读 M09 结果 | AI 先定；不包含完整敌人决策系统 |
| M09 观测与内容生产 | 日志标识、失败原因、配置检查、重置观测、内容入口和能力缺口 | 汇总模块结果；调用其清理接口 | AI 先定；实际需要稳定后再固化 schema |

边界约定：

- M03 决定何时消耗资源、启动冷却；M05 执行数值修改。不能各自扣费。
- M03 决定引导/多段的阶段推进；M06 执行空间行为，不能另建一套施法状态机。
- M04 决定查询和命中合法性；M06 提供碰撞、区域或位移过程中的命中候选。
- M01 负责装配 UI 的操作含义；M07 负责通用反馈与资源接线。
- M02 协调单位死亡/重置；各模块清理自己拥有的状态和对象；M09 观察残留，不接管所有对象。
- 技能定义的内容身份由 M03 定义；可用集合与授予由 M02 管理；快捷槽位由 M01 管理。

## 模块文档标准

每份设计至少明确：

1. 职责、排除项和具体操作场景。
2. 正常流程及失败、取消、中断、过期、清理行为。
3. 输入输出、事件、状态及依赖的接口约定。
4. 内容配置、项目默认值、固定约束、运行时状态与程序自由实现部分。
5. 已确认事实、AI 建议默认值和真正阻塞实施的未决项。
6. 可观察的试玩检查点；未运行的设计不能标成已验证。

不为每个参数或函数建文件，也不在多份文档中复制相同规则。接口写到语义足够清楚即可，不要求先定最终 C++ 类名或配置格式。

## 策划、程序与 AI 的决策边界

### 策划侧决定

- 系统要支持的能力和明确不支持的范围；
- 玩家、AI 和测试看到的操作与结果；
- 技能阶段、目标、效果、状态、资源和冷却的业务语义；
- 哪些内容需要配置、哪些约束必须始终成立；
- 失败、取消、死亡、重置和清理时玩家应看到的结果；
- 首版默认规则和需要试玩调整的体验假设。

### 程序侧决定

- GAS 与 SkillLab C++ 的具体职责映射；
- `GameplayAbility`、`GameplayEffect`、`AbilitySystemComponent`、组件和 Actor 的组织方式；
- 配置数据在 DataAsset、DataTable、结构化文件或其他载体中的实现；
- 请求、实例、事件、日志和临时对象的存储与生命周期实现；
- 性能、线程、对象所有权、错误处理和 UE API 的技术细节。

### AI 侧负责

- 把策划语义整理成模块规格、配置草稿和实现任务；
- 检查模块之间的依赖、遗漏和矛盾；
- 根据程序提供的生产接口生成重复技能内容和测试数据；
- 根据运行日志和样本结果提出规则或能力缺口修改建议。

AI 可以提出程序方案，但不能把某个 C++/GAS 实现方式反过来当成策划规则。程序也不能为了方便实现，悄悄删掉第一层已经纳入的能力范围。

### GAS 的定位

GAS 是主要运行基础，不是策划文档本身。策划定义“技能、效果、状态和生命周期应该表现为什么”；程序将这些语义映射到 GAS 和 SkillLab 扩展。某项 GAS 原生能力不足时，进入 SkillLab C++ 扩展或受控配置接口，不通过每个技能单独写一套专用逻辑绕过公共系统。

### 配置的定位

配置由策划决定可调内容和业务含义，由程序决定载体、加载、校验和运行时接口。配置不等于任意字段都可改：固定约束仍由系统保证，配置只能在规定范围内改变技能内容。

## 哪些需要人过，哪些可以 AI 先定

建议由人按四组体验看方案，无须对九个模块逐字段回答：

- 玩家操作：装配、瞄准、确认、取消，与移动输入的冲突。
- 施法手感：前摇、消耗时点、中断和缓冲。
- 战斗规则：伤害护盾、控制、驱散、免疫和叠加。
- 持续行为：投射物/区域/位移在技能结束、死亡和重置时的结果。

AI 可以先起草全部模块，提供一套可修改的默认规则及理由。对象存储、日志结构、接口命名、资源回退等技术细节交程序选择。影响总体范围、显著改变体验或互相冲突的规则，需要突出展示；不能把“AI 建议”写成“用户已确认”。

这只是分工建议，不自动授权实现所有模块。

## 程序什么时候可以开始

### 现在：技术拆解可以开始

现有范围、总览和模块地图已足够供程序阅读现有实现，提出 GAS 接入、职责分配和首批工作项。九份模块稿不必全部写完；当前文档也不代表九个模块都已经能直接实现。

程序现在可以同时定义 GAS/C++ 映射和最小配置载体；策划文档不需要先写具体类名或资产字段。

### 首批代码：补齐与这批工作直接相关的约定

M01～M04 已有首版详细稿。程序在代码实施前仍需把以下约定映射成技术方案并指出冲突：

- 单位与 ASC 的归属、初始化、能力授予、死亡和重置。
- 技能身份、请求输入/结果、上下文、拒绝与开始后中断。
- 当前第一批技能的提交时点、扣费冷却、取消清理和目标输入。
- 输入、槽位、可用技能集合、预览与调用入口的职责。
- 一种可读取的技能定义和参数载体，以及日志和重复运行方式。

程序补充对应技术映射后，即可在代码实施获授权时开始。没有实质影响这批工作的未决规则，不阻塞开工；会影响结果的假设必须写进本批任务。空接口不算功能完成。

### 后续：按模块推进可玩的完整链路

建议第一批串起：单位初始化 → 技能装配 → 按键/测试请求 → 激活 → 简单效果与反馈 → 结束/重置。具体样本与参数由首批模块稿给出。随后按目标预览、投射物与区域、状态效果、引导多段与位移逐步扩展，并行补文档。

每批工作交接只需要：实现范围、相关文档、采用的默认值、输入输出与清理规则、观察方法、未覆盖范围。用少量样本边试边改，不另设重型正式验收关卡。
