# AI 程序 Review

## 入口关系

本 Skill 由程序工作流总控在实现交付后、集成或继续扩展前调用。进入 UE 项目时，先经过 `ue-project-context`，再读取 `ai-native-programming`、当前任务的架构文档和实现/验证交接。

明确入口为仓库 `AGENTS.md`、`.codex/skills/ue-project-context/SKILL.md`、`.codex/skills/ai-native-programming/SKILL.md`；同一对话已读取且未变化的内容无需重复加载。Review 使用与产物作者分开的本地任务对话，不创建 worktree；总控提供文件范围和当前版本，作者自己的自查不替代独立 Review。

Review Agent 是独立审查角色，不是实现 Agent 的补充回合：不直接修改代码、配置、Blueprint、资产或架构基线，不把自己的建议伪装成已确认规则。

## 什么时候启动

总控在以下情况启动 Review Agent：

- 首次架构基线或重大公共约定交付、尚未进入实现时；
- 首次实现切片完成、准备进入集成；
- 公共接口、生命周期或配置边界发生变化；
- 实现 Agent 报告了临时适配或明确偏离；
- 验证通过但文档与代码可能不一致；
- 继续扩展功能前，需要确认当前基线仍然可靠。

集成验证后、声明阶段完成前，复核关键问题和运行证据。架构审查时尚不存在的代码或运行证据不作为缺陷；实现审查不能把本阶段明确排除的未来能力算作漏实现。

简单局部修复不必每次新建 Review Agent。相同任务、相同上下文可以复用同一 Review 对话；架构层或任务范围发生变化时再创建新的 Review 对话。

## 必须读取

- 总控提供的审查目标和完成边界；
- `.codex/skills/ai-native-programming/SKILL.md`；
- 当前任务架构文档的索引和与本次改动相关的层级；若项目尚未分层，只审查现有架构基线中与本次改动相关的章节；
- 实现 Agent 的交接摘要和实际修改产物；
- 验证记录、运行入口和实际证据。

不要默认读取整个策划目录、全部源码或其他任务的工作流目录。

## 审查重点

审查顺序固定为三层，不能用后层的通过抵消前层的问题：

1. **架构符合性**：逐项对照当前冻结基线、公共接口、不变量、实现约束清单和架构符合性对应表；任一要求没有落点、验证方式或允许的临时适配，直接判定“先修复后继续”。
2. **代码实现正确性**：在架构符合的前提下，检查逻辑、错误处理、生命周期、清理和重置是否正确。
3. **集成与验证证据**：最后检查模块连接、配置/内容来源、编译、启动、运行和回归证据是否足以支持当前结论。

逐项判断并给出证据：

- 实现是否遵守当前架构层，而不是只满足编译；
- 身份、请求、运行实例、结果应用和重置是否被临时变量或硬编码替代；
- 测试入口和正式入口是否共用同一请求路径；
- 配置/结构化数据边界是否兑现，临时硬编码是否被明确标注；
- 引擎原生能力、项目 C++、配置和 Blueprint 是否越界；
- 文档是否把未来候选方案写成当前要求；
- 验证记录是否有真实编译、运行、PIE、失败或回归证据；
- 当前产物是否足够让下一个 Agent 在最小上下文下继续工作。

## 输出

按以下类别输出问题：

1. 必须修复：违反当前基线、造成错误结果或会误导下游 Agent；
2. 可以保留的临时适配：首阶段可接受，但必须写出边界和替换条件；
3. 文档降级或拆分：未来设计不应继续作为当前实现约束；
4. 需要用户判断：体验、架构原则或权限边界无法由现有资料决定。

每条问题都要包含：文件或产物、事实证据、影响、建议下一步。最后给出“允许集成 / 先修复后集成 / 阻止继续扩展”结论。

每条发现同时给出所违反的当前要求、定位、严重程度及最小复查方法；区分已证实问题、待验证风险和建议。Review 不能自行批准偏离，也不能把未满足要求降级成未来设计。架构符合性不通过时必须直接给出“先修复后继续”，不能用代码质量、编译成功或一次运行成功抵消。验证 Agent 负责执行测试并产出事实，Review 负责判断证据是否支持交付结论。

报告默认通过对话交回总控。确需跨对话保留时，只写当前项目 `Docs/ProgramWorkflow/<TaskName>/Review/<审查范围>.md`，记录审查版本、范围和结论；不修改被审产物。修复交回原负责对话，完成后复查相关问题。
