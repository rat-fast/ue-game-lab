# AI 程序 Review

## 入口关系

本 Skill 由程序工作流总控在实现切片交付后或继续扩展前调用。进入 UE 项目时，先经过 `ue-project-context`，再读取 `ai-native-programming`、当前任务的架构交接和实现交接。

明确入口为仓库 `AGENTS.md`、`.codex/skills/ue-project-context/SKILL.md`、`.codex/skills/ai-native-programming/SKILL.md`；同一对话已读取且未变化的内容无需重复加载。Review 使用与产物作者分开的本地任务对话，不创建 worktree；总控提供文件范围和当前版本，作者自己的自查不替代独立 Review。

Review Agent 是独立审查角色，不是实现 Agent 的补充回合：审查阶段不直接修改代码、配置、Blueprint、资产或架构基线，不把自己的建议伪装成已确认规则。只有审查结论为“允许继续”后，才可以在同一对话中按 `project-documentation` Skill 更新已核对的项目代码文档；文档同步不改变审查结论，也不允许借此修改被审实现。

## 什么时候启动

总控在以下情况启动 Review Agent：

- 首次架构基线或重大公共约定交付、尚未进入实现时；
- 首次实现切片完成、准备进入下一阶段；
- 公共接口、生命周期或配置边界发生变化；
- 实现 Agent 报告了临时适配或明确偏离；
- 实现交付的事实证据不足，或文档与代码可能不一致；
- 继续扩展功能前，需要确认当前基线仍然可靠。

阶段结论前复核关键问题和实现交付中的事实证据。架构审查时尚不存在的代码或运行证据不作为缺陷；实现审查不能把本阶段明确排除的未来能力算作漏实现。

简单局部修复不必每次新建 Review Agent。相同任务、相同上下文可以复用同一 Review 对话；架构层或任务范围发生变化时再创建新的 Review 对话。

## 必须读取

- 总控提供的审查目标和完成边界；
- `.codex/skills/ai-native-programming/SKILL.md`；
- 当前任务的架构交接包和与本次改动相关的基线章节；
- 实现 Agent 的架构符合性对应表、交接摘要和实际修改产物；
- 实现 Agent 提供的运行入口、事实证据和证据缺口。

如果本次修改涉及模块职责、代码地图、公共运行入口、配置或资产入口、功能到实现的映射或验证方式，还必须读取受影响的 `ProjectContext/` 文档，检查项目代码文档是否需要同步；若实现明确判断不影响这些项目事实，也必须读取该判断及其依据。只有完成三层审查并得出“允许继续”后，Review 才加载 `project-documentation` Skill，按真实产物更新受影响的项目代码文档。

不要默认读取整个策划目录、全部源码、其他任务或未被交接包列出的项目产物。

## 审查重点

审查顺序固定为三层，不能用后层的通过抵消前层的问题：

1. **架构符合性**：逐项对照当前冻结基线、公共接口、不变量、实现约束清单和架构符合性对应表；任一要求没有落点、验证方式或允许的临时适配，直接判定“先修复后继续”。
2. **代码实现正确性**：在架构符合的前提下，检查逻辑、错误处理、生命周期、清理和重置是否正确。
3. **验证证据**：最后检查实现交付中的模块连接、配置/内容来源、编译、启动、运行和回归证据是否足以支持当前结论。

逐项判断并给出证据：

- 实现是否遵守当前架构层，而不是只满足编译；
- 身份、请求、运行实例、结果应用和重置是否被临时变量或硬编码替代；
- 测试入口和正式入口是否共用同一请求路径；
- 配置/结构化数据边界是否兑现，临时硬编码是否被明确标注；
- 引擎原生能力、项目 C++、配置和 Blueprint 是否越界；
- 文档是否把未来候选方案写成当前要求；
- 验证记录是否有真实编译、运行、PIE、失败或回归证据；
- 当前产物是否足够让下一个 Agent 在最小上下文下继续工作。
- 项目代码文档是否准确反映当前真实产物；若代码事实已变化，且审查已允许继续，必须在本次 Review 对话中完成 `ProjectContext/` 同步后再交付最终结论，不能以任务架构交接或编译成功代替更新。

## 输出

按以下类别输出问题：

1. 必须修复：违反当前基线、造成错误结果或会误导下游 Agent；
2. 可以保留的临时适配：首阶段可接受，但必须写出边界和替换条件；
3. 文档降级或拆分：未来设计不应继续作为当前实现约束；
4. 需要用户判断：体验、架构原则或权限边界无法由现有资料决定。

每条问题都要包含：文件或产物、事实证据、影响、建议下一步。最后给出“允许继续 / 先修复后继续 / 阻止继续扩展”结论。

每条发现同时给出所违反的当前要求、定位、严重程度及最小复查方法；区分已证实问题、待验证风险和建议。Review 不能自行批准偏离，也不能把未满足要求降级成未来设计。架构符合性不通过时必须直接给出“先修复后继续”，不能用代码质量、编译成功或一次运行成功抵消。实现 Agent 负责执行必要验证并产出事实，Review 负责判断证据是否支持交付结论。

报告默认通过对话交回总控。阶段 Review 的结论影响阶段推进，必须写入当前任务已有的 Review/交接文档；其他局部无阻塞复查可以只通过对话交付。审查阶段不修改被审产物；放行后的项目代码文档同步必须报告修改的文档、依据和仍未验证的内容，文档同步失败时不得把阶段标记为完成。修复交回原实现对话，完成后复查相关问题。
