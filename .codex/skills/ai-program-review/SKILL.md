# AI 程序 Review

## 职责与入口

进入 UE 项目时，先经过 `ue-project-context`，再读取 `ai-native-programming` 和本 Skill。使用与作者分开的审查上下文，核对真实产物；作者自查不能替代独立 Review。

审查依据是用户目标、当前策划需求、适用的公共约定和真实代码。架构交接帮助定位和理解方案，不是脱离需求的完成标准。审查阶段不直接修改被审代码、配置、资产或方案，也不把自己的改进建议变成本次新增要求。

## 启动与读取

功能交付或存在具体结构风险时进行独立审查。局部修复复查受影响部分，可复用原 Review 上下文，不机械重跑整套流程。只有公共方案本身需要先确认时才做实现前审查，不因产生了一份架构说明就增加一轮放行。

读取总控给出的范围和版本、相关需求、架构交接、实际修改、实现摘要及验证入口。涉及共享接口或业务约定时补读相关章节；沿具体疑点查看直接上下游。不要默认加载全部策划、源码和历史中间产物。

## 审查重点

围绕实际改动检查，顺序按问题关联决定：

- **需求与范围**：当前行为是否完成；程序建议、配置最终取值或未来能力是否被误列为必做项。
- **结构与复用**：落点是否符合职责；是否重复已有机制、绕过公共路径、混入内容专用规则，或为假想需求引入额外框架和抽象。
- **实现正确性**：相关逻辑、接口、错误处理和资源处理是否正确；身份、生命周期、清理和重置只检查本次涉及的部分。
- **验证依据**：结果是否有足够的编译、运行或其他相应证据；验证是否覆盖本次行为和受影响的直接依赖，未验证项是否如实说明。
- **交接与文档**：下游能否定位真实入口，说明是否与代码一致，项目代码地图是否确有需要同步的变化。

缺少放行包、符合性表、三类读取清单或固定文档目录，本身不构成实现缺陷。需要阻塞的发现应指明具体需求或正确性风险；单纯偏好的写法、假想扩展和本阶段排除项作为建议，不据此阻止交付。已有明确公共约定仍需遵守；若约定或任务方案与用户需求冲突，报告冲突并交回总控处理，不自行修改标准让实现通过。

## 输出与后续

给出简明结论：当前需求是否达到可交付状态，哪些部分仍待修复或验证。每个实质问题包含定位、事实、影响和最小复查方式；区分阻塞问题、待验证风险和可选建议。没有相关问题时无需填空表或凑固定类别。

实现 Agent 负责运行验证，Review 可以只读核对产物和现有证据；发现证据不足时指出具体缺口，不默认要求新增一套验收工具。修复交回负责实现的 Agent，完成后仅复查相关问题。

结论和必要证据入口由总控保存在可检索的上下文包，确需长期交接时再写入现有任务文档。只引用结果摘要和证据位置，不要求存入原始编译日志或完整运行日志。

若代码职责、入口或映射已经改变，审查通过后可在同一对话中按 `project-documentation` 同步已核对的最小项目事实；该维护与审查分开说明，不借此改写被审实现。文档未同步时报告其缺口和影响，不能声称全部交付完成，也不把它一律描述成功能不可运行。
