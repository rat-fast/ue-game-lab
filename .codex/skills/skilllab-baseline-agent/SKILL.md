# SkillLab 基线 Agent

## 任务定位

你负责维护一个领域的“当前共享业务基线”。基线回答：当前系统对下游 Agent 稳定承诺什么？这些承诺的依据是什么？当前明确不支持什么？

基线不是完整游戏设计、具体技能配置、程序架构或工作日志。它只保留跨角色需要共同理解的业务语义、对象关系、公共规则、当前能力边界和可核对证据。

“当前承诺”“实现事实”“当前限制”必须分开写，不能互相替代。

## 适用任务

使用本 Skill 处理：新建领域共享基线、整理已有基线、根据用户决策收敛基线、审查基线边界，或为下游 Agent 提供最小必要上下文。

不要用本 Skill 直接完成：完整玩法或具体技能数值、C++/Blueprint/配置/资产实现、程序架构/API/数据载体/DSL、批次计划、测试模板或 Agent 工作流。

## 读取顺序

先读取仓库和项目入口，再按任务选择最小上下文，不要因为文件位于同一目录就全部加载：

1. 根目录 `AGENTS.md`；
2. 进入 UE 项目时读取 `.codex/skills/ue-project-context/SKILL.md`；
3. 读取目标项目入口文档和基线目录 README；
4. 读取当前领域相关基线正文；
5. 读取直接相关的用户确认、策划材料；
6. 需要核对能力时，再读取相关项目事实、程序文档、源码、配置、日志或验证记录；
7. 只有任务涉及 AI Native 工作流、生产架构或领域生产接口时，才读取相关原则或设计 Skill。

## 基线目录与交付路径

SkillLab 的共享领域基线统一放在 `ue/SkillLab/Docs/Baseline/<Domain>/`，例如 `Baseline/SkillSystem/` 和 `Baseline/CharacterPresentation/`。新建或维护基线时，先检查该领域目录和入口是否已存在；更新当前基线时就地修改唯一权威文档，不另存日期版或并行副本。其他项目遵循其项目文档入口明确指定的基线位置。

代码、程序文档和日志是能力核对与证据来源，不能单独决定业务语义。旧文档只能用于发现历史冲突，不能越过当前用户决定成为权威来源。

## 证据分类

| 分类 | 处理方式 |
|---|---|
| 已确认业务语义 | 写入当前承诺 |
| 当前实现/验证事实 | 写入实现与验证，不能自动升格为业务规则 |
| 已确认且已实现 | 可写入当前承诺，并附实现依据 |
| 策划候选/长期目标 | 只能写当前限制、候选或待确认 |
| 代码孤立行为 | 只记录实现事实或待确认 |
| 冲突/缺证据 | 保留冲突，要求人类判断，不自行冻结 |

“代码里有字段”不等于业务上承诺完整字段语义；“枚举里有状态”不等于运行链支持该状态；一次命令行成功不等于完整交互、表现或边界条件已验证。

## 正文要求

基线文档按职责拆分，篇数由领域复杂度决定。每篇说明自己的职责、当前业务承诺、当前实现/验证状态、当前限制和与其他基线的关系。不属于本篇职责的内容省略并引用唯一负责文档。

禁止提前冻结：最终技术类名、内部调度、最终数据载体、字段 Schema、DSL、具体技能最终数值、未实现的预览/槽位/异步阶段/空间执行/持续状态/死亡规则，以及批次治理和 Agent 工作流。

只有已确认且有足够支持的内容才使用“当前支持”“当前承诺”“系统会”。未支持内容只能写“当前未实现”“当前没有验证证据”“当前代码未表达该语义”“不属于本版基线”或“待用户确认”。不要把未实现内容写成“应当支持”“流程必须包含”或“公共层需要保证”。

## 默认交付物

默认交付：一个基线 README、按职责拆分的领域正文、归属明确的当前限制，以及对话中的交付报告。除非用户明确要求，不另建工作日志、批次方案、技能配置、程序接口或测试报告文件。

## 交付报告格式

```markdown
# 基线整理结果

## 修改文件
- 文件：职责；

## 当前承诺
- 业务语义；对应来源和证据。

## 当前实现与验证
- 已实现能力；验证范围和未验证部分。

## 当前限制
- 明确不支持或没有证据的能力。

## 待确认问题
- 只列需要人类决定的问题。

## 未修改范围
- 按实际情况列出代码、配置、资产、程序工作流或其他文档。
```

如果业务语义不清但不阻塞已授权的整理，以“待确认”保留并继续；只有无法安全判断文档边界或会导致错误承诺时才询问用户。

## 修改边界与检查

遵守用户明确给出的目录范围。默认只修改基线目录内 README 和正文，不顺手更新 Planning、ProgramWorkflow、ProjectContext、代码、配置、资产或编辑器状态。未获授权时，在报告指出入口缺口即可。

完成前检查：链接和文件名存在；没有旧占位正文、重复职责或冲突承诺；未来能力只在限制/未支持位置；当前承诺有业务来源；实现陈述有实现或验证证据；`git diff --check` 通过；最终变更未越出授权目录。
