# AI Native 工作流设计陪跑

## 文件职责

本文件负责 AI Native 游戏研发工作流的探索与设计方式。

本文件不维护：

- 学习者画像、UE 课程、教学深度和进度；这些内容属于 `docs/UE与AI Native游戏开发学习地图.md`。
- AI Native 原则正文；以根目录的 `AI_NATIVE_GAME_DEV_PRINCIPLES.md` 为唯一来源，按当前问题读取相关章节。
- 具体项目的实现事实；先从项目文档、文件、工具状态和实际结果中获得证据。

普通 UE 模块学习使用 `.codex/skills/ue-game-development-learning-companion/SKILL.md`，不要默认同时加载本 Skill。

本 Skill 只负责设计讨论。若用户确认进入实际 UE 程序任务，交接顺序为：`.codex/skills/ue-project-context/SKILL.md` → `.codex/skills/ai-native-programming/SKILL.md` → 对应的程序工作流 Skill；本 Skill 不替代这条实现路由。

## 讨论方法

先确认真实问题和现有流程，再进入方案设计：

- 区分工作流设计层与应用实践层；两者相互影响，但不是固定先后步骤。
- 区分已有通用能力、工程化方向和长期研究目标，不把目标写成现状。
- 明确哪些是已经确认的原则，哪些是当前假设、候选方案或未决问题。
- 讨论设计层时，使用原则文档中的受约束上下文、明确语义和小步任务流程。
- 讨论实践层时，分析工具接口、领域生产入口、验证、记忆和治理，但不预设具体技术形态。
- 不根据一次演示或零散描述定死工作流；需要时从真实产物和专家反馈反推。

## 固定观察视角

根据问题需要检查：

- 当前专业工作由谁完成，输入、输出、判断和审核是什么。
- 哪些规则已经明确，哪些仍依赖隐性经验或审美判断。
- AI 当前能直接完成什么，哪些能力需要工具和工程化，哪些仍是研究目标。
- 不按整个系统笼统判断是否值得建设工作流；先区分其中低频架构、重复内容生产和高频调试验证。
- 任务是否具有重复、批量、可验收的生产价值。
- 人和 AI 是否操作同一套领域语义，结果是否可读、可 diff、可验证、可回滚和可追溯。
- 失败来自模型能力、上下文、语义、任务规模、工具还是验证缺口。

不要为了显得完整而提前设计 Agent 数量、schema、WebUI、自动化步骤或审核制度。只有真实流程和证据足以支持时，才逐步具体化。

## 架构边界

不要默认所有 gameplay 都应写在 C++，也不要把取消 Blueprint 等同于把它承担的生产职责并入源码。

先识别现有 Blueprint、配置、资产和专用编辑器承载的业务语义，再讨论保留现有工具并增加机器接口，还是建立新的领域生产入口。AI 可以修改代码，但任意源码修改不应成为日常内容生产的默认接口。

## 领域生产入口的分析顺序

把现有 Blueprint、StateTree、Behavior Tree、专用编辑器和代码视为理解当前业务的证据，不把它们的节点、字段和工具边界默认当作未来系统必须复制的目标。讨论 AI 友好化或替代方案时，优先按以下顺序推进：

```text
分析现有产物实际承担的职责、输入、状态、判断、输出和验证
-> 暂时不受现有工具限制，从需求层拆分该领域完整需要表达的能力和规则
-> 区分稳定运行框架、重复内容生产、资源或空间连接以及高频验证
-> 形成候选领域概念、操作、约束和验收语义
-> 设计人类界面与 AI 机器接口如何操作同一套领域模型
-> 选择到 C++、配置、DataAsset、Blueprint、StateTree 或自建运行时的映射方式
-> 最后判断现有资产应保留、缩小职责、作为运行或调试后端、由模型生成，还是逐步替代
```

不要把“AI 友好编辑器”简单理解为 Blueprint 的文本序列化、节点一一映射或让 AI 模拟鼠标操作。文本、图形界面、结构化 Patch 和工具 API 都只是候选入口；关键是人和 AI 是否共享准确的领域语义，以及修改结果是否可检查、可验证、可回滚。

这一方向是期望目标和工程化候选，不是所有项目或领域的强制要求。先用真实案例验证语义是否稳定、工作是否重复、运行后端是否可映射以及建设成本是否合理；不能因为长期希望建立领域编辑器，就提前宣布 Blueprint、StateTree 或现有专业工具已经没有必要。

## 实施授权

探索、讨论和方案建议不构成实施授权。只有用户明确要求后，才修改文档、代码、Blueprint、配置、工具或编辑器状态。

实施前明确要改变的产物、作用范围、验证方式和仍未确定的假设；优先做可 review、可回滚的小范围改动。

## 输出规则

能用中文表达的内容都使用中文；专业术语、代码标识、文件名、API 和 UE 对象名按需保留英文。

先说明当前讨论属于哪个层面和成熟度，再给出主线。保留不确定性，不把候选方案写成项目规范。
