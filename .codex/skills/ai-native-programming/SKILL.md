# AI Native 程序开发约束

本 Skill 是程序 Agent 的 AI Native 约束入口，把仓库级原则转换成程序工作可以直接执行的要求。不负责项目代码地图、功能策划、专项实现或完整 AI Native 工作流设计。

进入 `ue/` 项目时，先读取 `ue-project-context`，获得仓库规则、项目文档入口和目录边界。涉及程序架构、C++、配置、Blueprint、模块实现、集成、编译或运行验证时，再读取本 Skill。`ai-native-design-collaborator` 只用于讨论 AI Native 工作流设计，不是程序实现对话的默认上下文。

项目专属程序职责和分层约定由该项目的上下文文档定义。进入 SkillLab 的程序 PM、架构、实现、集成或 Review 任务时，按 `ue-project-context` 路由读取 `ue/SkillLab/Docs/ProjectContext/ProgramArchitectureContract.md`；本 Skill 不复制该项目规范，也不把它套用到其他 UE 项目。

## 上下文边界

- 按 `ue-project-context` 的职责分支和本角色 Skill 取得当前任务最小但足够的上下文，不扫描整个仓库或整个 `Docs/`；地图/索引按定位需要读取，不能省略适用规范、需求与公共约定。
- 已完整提供且无变化迹象的内容复用；文件更新、上下文缺失或出现具体疑点时补读相关部分。并行读取要控制合并后的返回量，截断后只补缺失部分，不反复全文输出。
- 明确输入、输出、允许修改范围、依赖、验收方式和未决问题。
- 区分项目通用事实、当前任务策划和当前任务程序中间产物。
- 缺少影响方案的公共接口、体验规则或资源事实时，记录并回交总控，不自行补成已确认规则；局部代码事实可以沿直接依赖核对。

## 需求与实现范围

- 从用户目标和策划需求确定程序任务；配置内容的最终取值、未来设想和程序建议不能自动升级为本次要求。
- 架构交接用于说明现有运行链、复用点、职责和修改落点；按当前需求处理结构问题，不以完整冻结基线、放行包或符合性表作为所有任务的前置条件。
- 验证覆盖本次行为和受影响的直接依赖；先复用已有入口，只有现有方式不足以判断结果时才补必要工具。新增框架、持久化机制或验证设施需要说明当前需求中的具体用途。
- 实现提供事实证据，Review 判断需求、代码边界和结果是否成立；编译通过不等于功能或职责划分已经正确。

## 产物分层与维护边界

- 文档、代码、配置和验证记录均按职责、变化原因和读取对象分层；可独立理解、修改或交接的内容拆成模块或专题，通过明确接口和引用连接，避免集中到一个大文件，也避免为凑层数拆出空壳。
- 文档入口只保留范围、状态、公共约定和下游路由；模块细节、实现事实、验证证据、未来候选分别维护。每项规则保留一个权威来源，不复制多份正文；当前要求、已实现事实和未来建议必须区分。
- 项目代码文档记录当前真实代码，程序工作流文档记录任务判断和交接；二者互相引用，不互相复制。优先更新已有简明说明；长期框架、批次和专题目录只在确有独立维护需要时建立，不预建一套文档层级。
- 验证交付只保留可复现入口、结果摘要、证据位置和未验证项；原始编译日志、完整运行日志和日期化重复报告不作为长期程序文档。
- 修复由负责该产物的 Agent 完成。Review 不直接改写被审产物或增设需求；若任务方案本身过重，提出依据并交回总控修正，不能为了让实现通过而删掉真实需求或隐去问题。

## 代码与配置约束

- 新增稳定运行能力、状态机、校验、生命周期、日志和测试入口，默认优先使用 C++。
- 新增可变参数、重复内容、内容数值、资源引用和可批量调整内容，默认优先使用配置或结构化数据。
- 无论当前使用 C++、UE 资产还是外部数据，都必须把稳定运行机制、可变内容定义、测试适配和表现适配分开；测试样例也必须通过正式的请求、效果结果和事件接口，不能因“只是测试”把内容规则塞进通用生命周期代码。
- 若当前暂不引入 JSON、DataTable、脚本或其他载体，可以先用独立的类型化 C++ 定义提供器承载内容；这不允许把具体内容标识、数值、结果构造或内容分支直接写进通用请求、激活、扣费、冷却、清理和重置流程。说明当前权威来源和接口边界，不要求提前设计未来迁移系统。
- 需要频繁修改的内容必须有 AI 可读、可定位、可修改、可 diff 和可验证的权威入口。UE 二进制资产只能作为运行载体；若它是内容生产入口，必须同时提供可调用的编辑/导入/校验路径，或由文本源生成，不能要求 AI 只能手工点编辑器。
- 同一内容只能有一个权威来源。若存在 C++、文本源、UE 资产或导入产物之间的转换，必须明确源数据、生成步骤、同步检查和失败处理，禁止多处手工维护同一字段。
- Blueprint 默认用于兼容外壳、资源绑定、组件组装、默认值和 UE 编辑器必须承载的对象关系。
- 不把新的核心业务逻辑、跨模块规则或难以验证的状态机默认放进 Blueprint。
- 已有 Blueprint 主导的逻辑采用渐进处理，不为了形式上的纯 C++ 整体重写。
- 角色或 Actor 功能增长时按职责拆分类或组件，不把无关行为堆积到单个 Character 或 Blueprint 图。

## 验证和交回

- 每次修改说明修改产物、依据、接口影响和运行链影响。
- 优先使用可读、可 diff、可定位和可回滚的产物；资产修改说明资产入口和验证方式。
- 代码、配置或资产不是完成的唯一证据，需要编译、运行、PIE、日志或其他适合任务的验证证据。
- 已交接范围内的接口接入、普通类型、include、编译和局部连接错误可以继续修复；需要改变约定的公共接口、突破职责边界或决定未定义体验规则时，回交相应问题，不扩大整个任务范围。

## 交付

交付至少说明：读取的项目和任务文档、修改的产物、采用的 C++/配置/Blueprint 分工、已验证内容、未验证内容、需要总控或用户判断的问题。
