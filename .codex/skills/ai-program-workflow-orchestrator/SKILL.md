# AI 程序工作流总控

## 目标与分工

把用户目标和策划需求转换为有明确边界的程序工作，协调到可运行、可检查的结果。多 Agent 用于隔离上下文和关注点；任务拆分由功能和依赖决定，不从角色数量、文档数量或固定阶段反推工作。

总控负责范围、上下文、依赖和进度，不替专项 Agent 逐行实现。各职责如下：

| 角色 | 关注的问题 | 主要交付 |
|---|---|---|
| 架构 Agent | 相关运行链、现有能力、复用点、职责和改动影响 | 落盘的简明架构交接文档 |
| 实现 Agent | 在明确边界内完成行为、接入和事实验证 | 可检查的实现及结果摘要 |
| Review Agent | 独立核对需求、结构合理性、正确性和证据 | 有定位依据的问题和交付判断 |

新功能先由架构 Agent 梳理相关代码并确定落点，已有有效交接则只补本次变化，不重复开展完整架构设计。实现根据交接完成工作，Review 独立核对结果。角色边界保持清楚，不要求每个角色都建立一套文档或工具。

## Skill 与项目入口

启动时读取 `ue-project-context` 并完成其项目路由，再读取 `ai-native-programming` 和本 Skill。共用的编码与配置原则、需求和验证边界以 `ai-native-programming` 为准。专项 Agent 按职责读取：

- `ai-program-architecture`：相关代码梳理和改动设计。
- `ai-program-module-implementation`：功能实现、接入与验证。
- `ai-program-review`：独立审查。
- `project-documentation`：仅在需要维护当前项目代码地图或实现事实时加载。

总控按职责摘要调度，无需全文加载所有专项 Skill 或把它们的规则复制进任务。

## 确定工作范围

先读取用户当前目标、策划需求和项目代码地图。区分需求、配置内容、现有事实和程序建议；程序任务以需求为准，历史方案和架构中间产物不能自行增加验收项。相关需求原文应传给负责的 Agent，不只转述上一次任务理解。

在派架构 Agent 前，先按行为边界和直接依赖提出初步实现任务拆分：每个候选任务只需要有目标、预期依赖、可能的修改范围和验证入口，不提前冻结类名、接口或工具方案。初步拆分用于让架构 Agent 核对，不按策划文档数量或预设 Agent 数量机械决定任务数。

让架构 Agent 从真实入口核对相关上下游，说明已有能力、实际缺口和合适落点，并检查初步任务拆分是否能独立修改、验证和交付。架构 Agent 可以基于直接依赖、职责归属和验证入口合并、拆开或调整任务顺序；总控据此确定最终实现任务。不把所有新功能默认升级为全局架构重审，也不因已有代码存在就先安排一轮全量实现审计。

架构交接的内容和落盘要求以架构 Skill 为准。总控确认最终任务边界、每个任务的交接文档映射、范围和依赖已经清楚后分发实现，并将该任务对应的文档交给实现和 Review。任务入口只维护状态、需求入口和文档映射，不复述架构结论；不另要求完整冻结基线、放行包或逐条符合性表。只有需求无法决定、且不同选择会改变产品范围、运行语义或公共接口的问题才交由用户决定，并只阻塞依赖该决定的部分。代码/资产核对、原型验证及工具、格式、文件或模块落点等技术选择由负责 Agent 推进；技术验证发现明确需求无法实现时，再带证据和最小替代方案回交。其他工作继续。

## 上下文与任务交接

分发前说明本次目标和需求来源、允许修改范围、依赖、该任务的架构交接、代码/配置/资产入口，以及应交回的结果和实际验收方式。文件路径可直接打开，并简述用途。只传递该 Agent 需要的材料，不转发全部历史讨论和中间产物。

架构 Agent 查看相关运行链和上下游。默认每个稳定实现任务有独立交接文档，实现 Agent 只读取自己任务的需求段落、架构交接、落点文件和直接依赖，不默认读取其他实现任务材料或整个项目。若多个任务由同一实现单元承担且共享上下文，可以共用分节交接，但仍只要求读取相关章节。Review Agent 只读取当前被审任务所需的需求、架构交接、改动及证据。局部事实缺失可以沿依赖核对；会改变任务范围、公共约定或职责归属时再回交。上下文清单用于导航，不要求因漏列一个局部文件就停工。

拆分实现任务时按功能边界和依赖决定。每个任务的派发说明至少明确：任务目标、所需架构章节、必须读取的需求和文件、允许修改范围、不得触及的邻接范围、验证入口和交付路径。不要因为多个任务使用同一架构文档，就把整份文档复制到各自目录；也不要把无关任务合并到一个实现 Agent 以减少文档数量。

首次分发一个新的稳定实现任务时，可以使用当前环境提供的独立新对话，以隔离职责上下文并保留可检索的任务边界。同一功能、同一缺陷和同一实现负责人的局部修复、编译修复与回归验证，默认继续原实现对话，并把新的日志、错误和验证结果交回原负责人；不要因为出现一次新问题就重新创建完整实现任务。只有任务职责发生变化、原上下文已经混入无关内容、需要与作者隔离的独立判断，或用户明确要求隔离时，才创建新的实现对话。Review 仍使用与作者分开的审查上下文。若独立对话能力不可用，或用户明确要求使用子 Agent 协作，才使用子 Agent；此时仍需明确文件归属，避免并行修改同一产物。不得把使用多 Agent 扩展为默认创建新 worktree 或推送代码的授权。

## 产物和文档

项目文档按用途定位：

- `Docs/ProjectContext/`：当前代码事实、模块和运行入口。
- `Docs/Planning/<TaskName>/`：策划需求；共享业务约定从项目入口按需读取。
- `Docs/ProgramWorkflow/<TaskName>/`：需要保留的本任务判断和交接。

架构交接必须保存在位置明确、持续更新的任务文档中，默认每个稳定实现任务一份；只有多个任务由同一实现单元承担且共享上下文时才共用分节文档。总控在任务入口保留任务与文档的映射，入口只做导航，不重复架构结论，聊天或上下文包只引用、不替代文档。其他交付可复用已有文档或可检索的上下文包，局部修复不必另建报告。项目已有 `Batches/<BatchName>/` 时沿用相应位置；不预建 `LongTerm/`、架构、实现和 Review 全套目录。

项目代码文档只记录已经核对的事实，任务交接记录本次方案；不互相复制。实现交付指出职责、运行或配置入口是否变化，Review 核对后，确需同步时按 `project-documentation` 更新最小必要内容。

## 推进与 Review

先完成能看到行为结果的功能切片，再按证据处理后续问题；验证属于实现工作，判断证据属于 Review。复用已有编译和运行入口，只有存在明确缺口时才安排必要工具，不把完整验收设施作为所有功能的前置工程。

根据依赖串行或并行推进；接口未确定时不让依赖方各自猜测。接收交付后检查需求覆盖、实际修改和验证缺口，组织独立 Review。局部修复交回原实现 Agent，复查受影响部分；只有具体风险或重大公共决策需要时才增加实现前审查。

Review 的阻塞问题应有需求或正确性依据。发现方案本身超出需求时，回到需求修正方案，不继续围绕过重方案叠加流程，也不删掉真实要求来让当前实现通过。体验规则和职责冲突回交相应决定，其余工作继续。

## 状态与交付

持续报告已完成的行为、正在处理的具体问题、未覆盖范围和进入运行测试的剩余条件；代码行数、文档数量和工具建设不替代功能进度。总控保留必要的任务状态和交接入口，不复制各 Agent 全部过程。

结束时说明实际实现、Review 结论、验证结果及仍未完成或未验证的部分。代码可编译、功能可运行、文档已同步是不同事实，分别如实报告。
