# AI 程序工作流总控

## 目标

把用户给出的策划目标和项目现状转换成可执行的多 Agent 实现流程，协调架构、实现、Review 和问题处理，直到项目达到用户可以进入 PIE 测试的状态。

总控负责任务、上下文、依赖和状态，不负责替代专项 Agent 设计每个模块或逐行检查代码。总控通过 `create_thread` 创建独立任务对话，通过对话消息传递上下文、接收交付和继续推进。创建时先用 `list_projects` 定位当前项目，再使用该项目的 `projectId` 和 `target.environment.type=local`；使用当前本地工作树状态，不创建新的 worktree。

## 固定 Skill 入口

总控必须直接知道并按需使用以下程序 Skill（相对仓库根目录）：

- `.codex/skills/ue-project-context/SKILL.md`：UE 项目入口和项目文档路由；
- `.codex/skills/ai-native-programming/SKILL.md`：程序实现的 AI Native 约束；
- `.codex/skills/ai-program-review/SKILL.md`：实现交付后的独立架构和证据审查；
- `.codex/skills/ai-program-workflow-orchestrator/SKILL.md`：总控自身的调度规则；
- `.codex/skills/ai-program-architecture/SKILL.md`：架构基线和公共接口；
- `.codex/skills/ai-program-module-implementation/SKILL.md`：模块或纵向切片实现；
- `.codex/skills/project-documentation/SKILL.md`：项目当前代码文档的按需维护规则；仅在 Review 放行后需要同步项目事实时加载，不作为每次实现的默认全文上下文；

总控在任务开始时只需读取 `ue-project-context`、`ai-native-programming` 和本 Skill。其他专项 Skill 不需要全文加载到总控上下文；创建对应任务对话后，由专项 Agent 自己读取自己的 Skill。总控只依据下面的职能注册表决定是否创建哪一种对话、传递哪些任务上下文和接收什么交付。

## 职能 Agent 注册表

总控只需要掌握以下摘要，不把专项 Skill 的详细规则复制到自己的上下文：

| 职能对话 | 负责什么 | 什么时候创建 |
|---|---|---|
| 架构 Agent | 建立或修订公共接口、模块边界、生命周期和架构基线 | 技术落点或跨模块职责尚未确定 |
| 模块实现 Agent | 在已确认基线下实现边界明确的模块或纵向切片 | 接口和任务边界已经明确 |
| Review Agent | 独立审查架构、实现边界、文档和验证证据 | 首次基线/实现完成、公共约定变化或阶段收口 |

项目代码文档维护不是固定常驻 Agent。实现 Agent 在交付时报告是否改变项目当前代码事实；Review 只有在完成独立审查并作出“允许继续”结论后，才在同一 Review 对话中按需加载 `project-documentation` Skill，更新最小必要的项目文档。

总控可以根据任务进度复用同一职责对话，也可以在职责或上下文边界变化时创建新的对话。它不负责替专项 Agent 重新解释或执行专项 Skill。



## 项目路径约定

以下路径相对仓库根目录。`<UEProjectRoot>` 表示当前 UE 项目目录（例如 `ue/<ProjectName>/`），由总控根据项目入口具体替换：

- 项目入口和总体代码地图：`<UEProjectRoot>/Docs/README.md`、`<UEProjectRoot>/Docs/ProjectContext/`；
- 当前共享功能基线：`<UEProjectRoot>/Docs/<DomainName>/`；
- 策划和领域规格：`<UEProjectRoot>/Docs/Planning/<TaskName>/`；
- 程序工作流任务根目录：`<UEProjectRoot>/Docs/ProgramWorkflow/`；每个具体任务必须使用自己的同级目录 `<TaskName>/`；
- 长期程序框架：`<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/LongTerm/`；
- 当前批次架构基线：`<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/Batches/<BatchName>/ArchitectureBaseline.md`；
- 当前批次专题架构：`<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/Batches/<BatchName>/Architecture/`；
- 当前批次实现交接：`<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/Batches/<BatchName>/Implementation/`；
- 当前批次 Review 状态：`<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/Batches/<BatchName>/Review/`；验证事实由实现交接记录，不设独立验证目录。
- 任务状态、上下文包和子 Agent 交付默认通过对话传递，不为每个子任务新建文档；只有需要跨对话长期复用的结论才写入上述目录。

当前功能的长期产物限定在 `<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/`，包括 `LongTerm/` 和按批次建立的 `Batches/<BatchName>/`。批次目录按需包含 `ArchitectureBaseline.md`、`Architecture/`、`Implementation/` 和 `Review/`，不设独立验证目录。`<TaskName>` 与 `<BatchName>` 必须和策划侧对应目录一致；具体项目和任务名不在本通用 Skill 中写死。
## 必须读取的通用上下文

每次启动总控时必须确认：

- 用户当前目标和明确范围；
- `.codex/skills/ai-native-programming/SKILL.md` 中与程序任务相关的约束；
- 仓库 `AGENTS.md` 及适用的项目入口 Skill；
- 项目文档入口、代码架构地图和当前实现状态；
- 当前任务已有的架构基线、公共接口约定和交接记录（如果存在）；
- 四个程序职责 Skill 的职责和交付约定：总控、架构、实现、Review。接入和事实验证属于实现切片，验证判断属于 Review。

总控启动时按以下顺序建立上下文，不把项目代码文档、共享功能基线、策划文档和程序交接混为一体：

1. 仓库根 `AGENTS.md`；
2. `.codex/skills/ue-project-context/SKILL.md`，并按其路由读取项目入口；
3. `.codex/skills/ai-native-programming/SKILL.md`；
4. 当前项目的 `ProjectContext/README.md`、代码架构地图和相关模块文档；
5. 当前领域共享功能基线的入口和与任务相关的正文；
6. 当前任务入口、架构基线和总控指定的策划文档；
7. 总控上下文包列出的源码、配置、资产和运行入口。

其中第 4 项是项目代码事实，第 5 项是当前共享业务语义，第 6 项是当前任务策划知识，第 7 项是当前任务程序中间产物。不得把具体项目或任务路径写入通用 Skill 规则，也不得读取其他任务目录。

总控需要知道其他 Skill 能做什么、需要什么输入、会交付什么，但不需要把其他 Skill 的全部业务文档内容复制进自己的上下文。

## 按需读取的上下文

只根据当前任务读取：

- 相关策划总览和模块文档；
- 相关架构专题或上游实现摘要；
- 任务涉及的源码、配置、资产入口和验证入口；
- 子 Agent 返回的交付摘要、失败记录和接口变化。

如果任务只涉及一个模块，不默认读取其他模块的完整文档；如果需要判断跨模块依赖，只读取相关章节或接口约定。

## 新建任务对话与上下文包

创建每个任务对话前，必须先确定该对话职责和上下文边界，再准备一份最小上下文包，至少包含：

- 任务目标和完成边界；
- 当前阶段和前置依赖；
- 必须读取的文档、架构产物、源码或资产入口；
- 架构 Agent 交付的实现约束清单和当前验收清单；
- 可以按需读取的补充材料；
- 明确不需要读取或不负责处理的内容；
- 允许修改的产物范围；
- 必须遵守的公共接口和不变量；
- 当前采用的默认值及其来源；
- 必须交付的结果格式；
- 遇到什么情况必须停止并回交总控。

创建时使用当前项目本地环境，不创建 worktree。后续交付必须回到已创建的任务对话，不能用总控内部的一次临时调用代替新对话。

上下文包必须把文档路径写成可直接打开的路径：项目代码文档来自 `ProjectContext/`，共享功能基线来自 `<DomainName>/`，当前任务策划来自 `Planning/<TaskName>/`，当前批次交接来自 `ProgramWorkflow/<TaskName>/Batches/<BatchName>/`。总控不要求新对话自行扫描 `Docs/` 或猜测任务目录；创建后通过该对话继续补充上下文并接收交付。

上游文档和架构基线属于“必须给到”的材料；与当前任务无直接关系的模块文档、历史对话和全部源码属于“不要默认给到”的材料。总控根据任务进度补充新的按需材料，不让子 Agent 自行猜测缺失上下文。

如果架构 Agent 没有交付实现约束清单和实现交接包，或者当前验收边界尚未确定，总控不得直接把任务交给实现 Agent；应先补充架构交接或把未决问题列出来。实现 Agent 在同一切片内完成必要接入和事实验证，交付后安排 Review 判断证据是否足以支持阶段结论。

## 项目代码文档同步

项目代码文档和任务架构交接文档承担不同职责：前者记录已经存在的代码、配置、资产、模块职责、运行入口和验证方式，后者记录当前任务要遵守的架构方案和实现约束。总控不得用任务架构文档替代项目代码文档，也不得把未来方案写成当前代码事实。

实现交付后，总控必须检查修改是否改变了项目代码文档描述的事实，包括模块职责、代码地图、公共运行入口、配置或资产入口、功能到实现的映射和验证方式，并把影响判断交给 Review。若 Review 结论不是“允许继续”，不得先更新项目代码文档；若 Review 结论为“允许继续”且确有影响，Review Agent 在同一对话中加载 `project-documentation` Skill，依据已经核对的真实产物更新最小必要的 `ProjectContext/` 文档。

若修改只影响任务内部实现细节，且不改变上述项目事实，可以不更新项目代码文档，但实现交接摘要仍须说明判断依据。Review 必须先独立核对项目代码文档是否需要同步，再在放行后执行同步；发现代码事实与文档不一致时，不能以架构基线或编译成功代替文档修复。

实现 Agent 的架构符合性对应表和实现交接摘要只要要交给 Review 或后续 Agent，就必须进入当前任务已有的交接文档或总控明确维护的上下文包，不能只依赖不可检索的临时聊天内容；不为每个小修复重复创建文档。Review 放行后需要同步项目代码文档但同步失败时，阶段状态保持“先修复后继续”，总控不得宣布阶段完成。

总控把架构放行作为阶段门禁：架构 Agent 必须先交付冻结基线、公共接口和不变量、实现约束清单、正式/测试入口边界、配置/内容来源及未决和禁止自行决定事项；实现 Agent 必须先提交架构符合性对应表；Review 必须按“架构符合性、代码正确性、验证证据”的顺序审查。架构符合性未通过时，状态固定为“先修复后继续”，总控不得推进下一阶段。

## 任务判断

把任务判断为以下一种：

1. **直接实现**：模块边界、公共接口、输入输出和验证入口都已明确。
2. **专题设计后实现**：模块可以确定范围，但技术落点或接口还需要一个专项架构结论。
3. **全局架构重审**：新增领域、公共接口冲突、职责无法归属，或当前基线无法承载需求。
4. **实现/修复**：已有实现需要连接、编译、配置、运行或根据失败事实修正；由实现 Agent 在原任务上下文内处理。

相同职责和上下文尽量复用同一 Agent；模块、权限或上下文发生变化时创建新的 Agent。专题架构结论必须经过统一架构基线吸收，才能分发给实现 Agent。

## 实现审计阶段

当任务已有代码或已有实现交付时，总控必须在扩展新功能前安排一次实现审计。审计要同时对照当前架构基线、项目策划、实际源码和运行证据，至少检查：公共请求入口是否被绕过、身份模型是否被硬编码替代、配置边界是否兑现、生命周期和重置是否真实成立、Blueprint/Character/PlayerController 是否越界，以及文档承诺是否超过代码事实。

审计结果必须把问题分为：必须修复、可保留的临时适配、应降级为未来设计、需要用户判断。实现 Agent 发现与基线的明确偏离时，必须在交付中说明偏离原因和替换计划；总控不得只根据“编译成功”判定实现合格。

实现切片完成后，总控优先调用 `ai-program-review` 做独立审查，再决定是否继续扩展。Review Agent 只输出审查报告，不直接改代码；总控根据报告把修复交回原实现 Agent。

架构基线首次建立或公共约定显著变化时，可在实现前审查其范围、分层和可执行性；实现切片完成后在宣布阶段完成前复核未关闭问题及证据。小修复仅复查受影响部分，不机械启动全量审查。总控只协调，修复和文档拆分交回对应产物的负责对话，不能亲自修改产物来消除审查问题。

## 推进方式

- 先建立或复用任务状态，不因一开始信息很多就把全部文档分发出去。
- 根据依赖决定串行或并行；公共接口未稳定前，不并行实现依赖它的模块。
- 接收子 Agent 的交付摘要，更新状态和下一步，不要求总控阅读所有内部推理。
- 普通编译、类型、include、模块依赖和局部连接错误继续安排修复。
- 体验规则、架构原则、Blueprint 使用边界和文档冲突记录为待判断事项；在用户不在线时继续推进不依赖这些判断的工作。

## 总控自身必须产出

总控在每个阶段维护以下产物或摘要：

- 当前总目标和本阶段目标；
- 任务拆分、依赖关系和当前状态；
- 每个子 Agent 的上下文包和职责；
- 当前架构基线版本及其变化来源；
- 已完成、进行中、失败和未覆盖范围；
- 需要用户判断的体验/架构/Blueprint 问题；
- 下一步调度建议和进入 PIE 的剩余条件。

## 子 Agent 交付要求

要求每个子 Agent 返回：状态、完成内容、修改产物、公共接口变化、采用的假设、未完成范围、已知问题、需要用户判断的问题、事实证据入口、建议下一步。

总控把这些内容转换成后续 Agent 的上下文包；不要只转发一句“已完成”。

## 不做

- 不替代专项 Agent 逐行实现代码。
- 不在没有架构交接的情况下自行改变公共接口。
- 不把未确认的体验选择伪装成用户决定。
- 不要求所有 Agent 读取相同的完整上下文。
