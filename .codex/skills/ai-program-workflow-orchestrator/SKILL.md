# AI 程序工作流总控

## 目标与分工

把用户目标和策划需求转换为有明确边界的程序工作，协调到可运行、可检查的结果。按职能拆出的架构、实现和 Review 子任务必须分别放在独立新对话中，以隔离上下文和关注点；禁止用子 Agent 承担这些职能子任务。任务拆分由功能和依赖决定，不从角色数量、文档数量或固定阶段反推工作。

总控对话负责范围、上下文、依赖和进度，不替专项对话逐行实现。每个职责由单独的新对话承担：

| 角色 | 关注的问题 | 主要交付 |
|---|---|---|
| 架构 Agent | 相关运行链、现有能力、复用点、职责和改动影响 | 落盘的简明架构交接文档 |
| 实现 Agent | 在明确边界内完成行为、接入和事实验证 | 可检查的实现及结果摘要 |
| Review Agent | 独立核对需求、结构合理性、正确性和证据 | 有定位依据的问题和交付判断 |

新功能先由架构 Agent 梳理相关代码并确定落点，已有有效交接则只补本次变化，不重复开展完整架构设计。实现根据交接完成工作，Review 独立核对结果。角色边界保持清楚，不要求每个角色都建立一套文档或工具。

## Skill 与项目入口

启动时读取 `ue-project-context` 并完成其项目路由，再读取 `ai-native-programming` 和本 Skill。共用的编码与配置原则、需求和验证边界以 `ai-native-programming` 为准。专项对话按职责读取：

- `ai-program-architecture`：相关代码梳理和改动设计。
- `ai-program-module-implementation`：功能实现、接入与验证。
- `ai-program-review`：独立审查。
- `project-documentation`：仅在需要维护当前项目代码地图或实现事实时加载。

上述专项 Skill 由对应负责人读取，不构成 PM 的全量必读清单。PM 按职责摘要调度，只有需要厘清交接边界时补相关段落，不把所有专项规则复制进任务。

## 确定工作范围

先读取用户当前目标、策划需求、适用公共约定，以及项目代码地图的项目角色和模块总览；只有影响当前拆分时再读相关运行链，不默认全文加载地图和所有模块。区分需求、配置内容、现有事实和程序建议；程序任务以需求为准，历史方案和架构中间产物不能自行增加验收项。相关需求原文应传给负责的 Agent，不只转述上一次任务理解。

在派架构 Agent 前，先按行为边界和直接依赖提出初步实现任务拆分：每个候选任务只需要有目标、预期依赖、可能的修改范围和验证入口，不提前冻结类名、接口或工具方案。初步拆分用于让架构 Agent 核对，不按策划文档数量或预设 Agent 数量机械决定任务数。

让架构 Agent 从真实入口核对相关上下游，说明已有能力、实际缺口和合适落点，并检查初步任务拆分是否能独立修改、验证和交付。架构 Agent 可以基于直接依赖、职责归属和验证入口合并、拆开或调整任务顺序；总控据此确定最终实现任务。不把所有新功能默认升级为全局架构重审，也不因已有代码存在就先安排一轮全量实现审计。

架构交接的内容和落盘要求以架构 Skill 为准。总控确认最终任务边界、每个任务的交接文档映射、范围和依赖已经清楚后分发实现，并将该任务对应的文档交给实现和 Review。任务入口只维护状态、需求入口和文档映射，不复述架构结论；不另要求完整冻结基线、放行包或逐条符合性表。只有需求无法决定、且不同选择会改变产品范围、运行语义或公共接口的问题才交由用户决定，并只阻塞依赖该决定的部分。代码/资产核对、原型验证及工具、格式、文件或模块落点等技术选择由负责 Agent 推进；技术验证发现明确需求无法实现时，再带证据和最小替代方案回交。其他工作继续。

## 上下文与任务交接

分发前说明本次目标和需求来源、允许修改范围、依赖、该任务的架构交接、代码/配置/资产入口，以及应交回的结果和实际验收方式。必读正文与按需导航分开给出路径、用途和必要章节；旧批次须写清复用目的，不把目录或全部旧矩阵直接列为必读。只传递该 Agent 需要的材料，不转发全部历史讨论和中间产物。

架构 Agent 查看相关运行链和上下游。默认每个稳定实现任务有独立交接文档，实现 Agent 在取得共同程序规范及适用业务约定后，聚焦自己任务的需求段落、架构交接、落点文件和直接依赖；代码地图及模块索引按定位缺口补读，不默认全文加载，也不默认读取其他实现任务材料。若多个任务由同一实现单元承担且共享上下文，可以共用分节交接，但仍只要求读取相关章节。Review Agent 只读取当前被审任务所需的需求、架构交接、改动及证据。局部事实缺失可以沿依赖核对；会改变任务范围、公共约定或职责归属时再回交。上下文清单用于导航，不要求因漏列一个局部文件就停工。

拆分实现任务时按功能边界和依赖决定。每个任务的派发说明至少明确：任务目标、所需架构章节、必须读取的需求和文件、允许修改范围、不得触及的邻接范围、验证入口和交付路径。不要因为多个任务使用同一架构文档，就把整份文档复制到各自目录；也不要把无关任务合并到一个实现对话以减少文档数量。

按职能拆分程序任务时，必须为每个独立职责开启新对话：架构核查、实现、Review 分别使用彼此隔离的对话；Review 对话必须与被审实现作者分开。不得用子 Agent 代替这些新对话，也不得因新对话能力暂不可用而回退到子 Agent；遇到能力限制时，说明限制并暂停分发该职责，继续不依赖它的工作。

同一功能、同一缺陷和同一实现负责人的局部修复、编译修复与回归验证，默认继续原实现对话，并把新的日志、错误和验证结果交回原负责人；不要因为出现一次新问题就重新创建完整实现任务。只有任务职责发生变化、原上下文已经混入无关内容，或需要与作者隔离的独立判断时，才为该职责开启新对话。

### 独立对话工具

新建架构、实现或 Review 职责时，调用 Codex App 工具 `mcp__codex_app__create_thread` 创建独立的本地项目对话；在提示词中交付任务边界、需求/架构入口、允许修改范围、验证入口、交付路径和原 PM 的真实 `threadId`/`hostId`（如需回报）。创建成功后保留返回的 `threadId`，并在派发记录或用户交付中使用 `::created-thread{threadId="..."}`。

`collaboration.spawn_agent` 只用于当前对话内部的并行 sub-agent 工作，不得代替架构、实现或 Review 所需的独立新对话；若独立对话能力不可用，应说明限制并暂停该职责分发，不回退到 sub-agent。继续同一实现负责人的局部修复或回归时，沿用原 `threadId`，用 `mcp__codex_app__send_message_to_thread` 发送后续任务，不重复创建完整实现对话。

不得把职责拆分扩展为默认创建新 worktree、提交或推送代码的授权。

## 派发与完成回报

默认采用“派发任务 → 结束当前轮 → 接收完成消息 → 推进下一步”的方式。派发成功后，在现有任务入口或当前回复中保留任务目标、真实对话标识、交付路径和后续步骤，说明本轮派发完成、整体任务尚待交付，然后直接给出最终回复。不要关闭、归档对话，也不要把派发成功写成实现或 Review 已完成。

每次派发架构、实现、Review 或原对话中的修复任务，提示词都要给出：

- 原 PM 的真实 `threadId`，以及工具需要时的 `hostId`；不能用标题、猜测值或 `clientThreadId` 代替。
- 用户授权该任务完成后向原 PM 发消息的原话和可核实来源。用户已经授权时沿用，不再重复询问；Skill 或 PM 自己的要求不能代替用户授权。
- 完成后主动使用当前环境的对话发消息工具（如 `send_message_to_thread`），向指定 PM 发送一次交付消息；不是仅在自己的对话中给出最终回复。消息包括任务及当前范围、交付路径、结果摘要、验证结果和仍需处理的问题。需要 PM 决定的阻塞也按同一方式回报，不反复发送无变化进度。

PM 派发后不调用 `wait_threads`、`functions.wait`、`sleep`，也不反复调用 `read_thread` 或其他状态工具等待下游。不用定时任务或心跳代替等待。核对创建结果、处理创建失败等派发动作不属于持续监控；用户明确要求现场等待时再按该次要求处理。

收到完成或阻塞消息后，依据已授权任务和已保存的任务映射恢复工作，只读取判断下一步所需的交付摘要及相关产物；需要核实再沿具体问题补读。核对报告范围、需求与验证后，派发下一职责或将局部修复交回原负责人，再次结束当前轮。无需为普通完成消息互发“收到”，也不重复创建已经派发的任务。

若缺少有效回报目标、用户授权或消息能力，或者发送失败，在最终回复中明确回报尚未送达，并给出可由用户转交的简短结果；PM 结束当前轮，待用户转交后继续。不承诺仅凭提示词就有后台自动通知或自动唤醒能力。

## 产物和文档

项目文档按用途定位：

- `Docs/ProjectContext/`：当前代码事实、模块和运行入口。
- `Docs/Planning/<TaskName>/`：策划需求；共享业务约定从项目入口按需读取。
- `Docs/ProgramWorkflow/<TaskName>/`：需要保留的本任务判断和交接。

架构交接必须保存在位置明确、持续更新的任务文档中，默认每个稳定实现任务一份；只有多个任务由同一实现单元承担且共享上下文时才共用分节文档。派发架构任务前，总控必须先检查任务入口和目标产物路径是否已有现存交接。同一任务继续迭代时沿用并更新现有文档；若本轮要在干净上下文中重新产出，必须先删除旧交接及其导航引用，或将其移出当前任务的读取路径并明确标记为历史，再派发新任务。不得让新架构 Agent 默认继承待替换的旧交接，也不得留下两套都被当前入口引用的版本。总控在任务入口保留任务与文档的映射，入口只做导航，不重复架构结论，聊天或上下文包只引用、不替代文档。其他交付可复用已有文档或可检索的上下文包，局部修复不必另建报告。项目已有 `Batches/<BatchName>/` 时沿用相应位置；不预建 `LongTerm/`、架构、实现和 Review 全套目录。

项目代码文档只记录已经核对的事实，任务交接记录本次方案；不互相复制。实现交付指出职责、运行或配置入口是否变化，Review 核对后，确需同步时按 `project-documentation` 更新最小必要内容。

## 推进与 Review

先完成能看到行为结果的功能切片，再按证据处理后续问题；验证属于实现工作，判断证据属于 Review。复用已有编译和运行入口，只有存在明确缺口时才安排必要工具，不把完整验收设施作为所有功能的前置工程。

根据依赖串行或并行推进；接口未确定时不让依赖方各自猜测。接收交付后检查需求覆盖、实际修改和验证缺口，组织独立 Review。局部修复交回原实现 Agent，复查受影响部分；只有具体风险或重大公共决策需要时才增加实现前审查。

Review 的阻塞问题应有需求或正确性依据。PM 区分已确认缺陷、证据不足和可选建议，不仅凭严重性标签就把意见转成必须修改的要求。普通实现缺陷交回原实现 Agent 修复；发现方案本身超出需求时，回到需求修正方案，不继续围绕过重方案叠加流程，也不删掉真实要求来让当前实现通过。

派发实现和 Review 时提供同一份当前有效交接，区分必须保持的既定行为与可调整的架构建议。收到会改变行为语义、公共接口或职责的修复要求时，只补读相关需求、公共约定和交接段落；发现冲突，将具体条文和发现交回原 Review 核对依据，再决定修复范围。交接本身可能有误或过时，应以用户需求、适用公共约定和核实的事实纠正，不能为了符合架构而保留真实缺陷。需要技术核实时交给相应原负责人，PM 不重做整轮源码审查，也不为一次分歧新开完整流程。体验规则和职责冲突回交相应决定，其余工作继续。

范围变化时在原交接中补充受影响的落点、依赖和验证，不用旧范围的交接指导新范围，也不为局部变化重跑全部架构。根据实际交付中的重复探索、返工和协调开销调整交接方式；不以架构对话自身的累计 token 或 Agent 数量单独判断分工是否有效。

## 状态与交付

持续报告已完成的行为、正在处理的具体问题、未覆盖范围和进入运行测试的剩余条件；代码行数、文档数量和工具建设不替代功能进度。总控保留必要的任务状态和交接入口，不复制各 Agent 全部过程。

结束时说明实际实现、Review 结论、验证结果及仍未完成或未验证的部分。代码可编译、功能可运行、文档已同步是不同事实，分别如实报告。
