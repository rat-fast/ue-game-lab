# AI 程序架构

## 职责

先看清现有代码如何协作，再为本次需求找到合适的修改或新增位置，让后续每个实现 Agent 都能在只读取必要上下文的条件下正确工作。架构 Agent 关注相关上下游和结构，实现 Agent 关注具体实现；职责分开不意味着必须先建设完整框架。

进入 UE 项目时，先按 `ue-project-context` 读取项目入口，再读取 `ai-native-programming` 和本 Skill。共用的编码、配置分离和验证原则以 `ai-native-programming` 为准，本 Skill 只规定结构分析和交接。

## 输入与读取范围

- 用户目标、策划需求及明确排除项；以需求确定程序工作，不从既有程序方案反推需求。
- 总控提出的初步实现任务拆分、任务依赖和预期修改范围；这些只是待核对的工作假设，不是架构结论。
- 项目代码地图中的模块关系和本任务相关主运行链、相关模块事实，以及总控指定的现有接口或交接；按结构影响补读其他章节，不默认通读所有模块或历史批次。
- 对应的真实源码、配置和资产入口；文档用于定位，结构判断要核对实际产物。

从相关功能入口沿直接调用、事件和数据依赖查看上下游，直到能解释运行链、现有能力和修改影响。已有交接可复用时，只核对与本次改动相关的部分。无需遍历全仓库，也不能只看单个待修改文件就决定方案。缺少关键事实时按依赖补读，说明仍未确认之处。

## 核对实现任务边界

先检查总控提出的初步任务拆分是否符合真实代码边界：哪些任务可以独立修改和验证，哪些任务共享同一职责或公共接口，哪些任务必须串行。根据直接依赖、职责归属和验证入口，可以建议合并、拆开或调整顺序；说明依据和影响，不按策划文档数量、角色数量或预设 Agent 数量机械拆分。只有确实共享不可分割的职责/接口，或无法独立修改与验证时，才把合并写成必要结论；否则保留总控按上下文和实施安排分配任务的空间。

架构交接默认按核对后的稳定实现任务分别落盘，使每个实现 Agent 可以只读自己任务的交接。总控入口文档只维护任务、需求和交接路径的映射，不复述架构结论。仅当多个任务由同一实现单元完成、共享同一组实现上下文时，才考虑共用一份按任务分节的交接；即使共用，也不能要求实现 Agent 阅读无关章节。不要为了凑文档数量拆出没有独立职责的任务。

## 分析与改动设计

围绕本次需求回答：

- **当前运行链**：功能从哪里进入、经过哪些对象、如何产生结果；需要关注的配置和表现入口在哪里。
- **现有能力与复用点**：引擎和项目已经提供什么，哪些可以直接使用，真正缺的能力是什么。
- **职责归属**：本次运行逻辑、内容定义、表现和测试分别由谁负责，避免把无关变化塞进一个类或文件。
- **修改落点与影响**：修改现有实现还是增加独立职责，涉及哪些文件和接口，会影响哪些直接依赖。

选择能满足当前需求且职责清楚的方案。低耦合要体现在依赖关系和独立修改能力上，不以新增类、接口层或文件数量证明。复用已有能力不等于为了假想变体提前抽象；多个地方需要相同机制时，也不要复制公共逻辑。

公共接口、对象身份、生命周期、清理等只在本次改动涉及或影响它们时展开。需要新增公共能力时，解释现有能力为什么不够，并设计当前调用方确实需要的接口。重大跨模块调整另列影响和待决定事项，不把局部任务扩展成全局重构。

复用结论优先由现有调用点或本次需求中的案例支持；没有当前案例时说明适用边界，不为证明“可扩展”额外增加样例、内容或测试框架。当前配置载体和权威来源需要清楚，但不要求预先设计未来迁移体系。

## 交给实现 Agent 的说明

必须为每个稳定实现任务交付落盘的简明架构交接；若任务由同一实现单元承担且共享上下文，才可共用一份分节文档。总控需要维护任务与文档的明确映射。每份交接服务于对应实现任务的上下文边界，只写该任务直接需要的信息：

- 本次要实现的行为、需求来源和范围。
- 相关运行链、可复用接口和已经确认的职责边界。
- 建议修改或新增的文件、接入位置，以及需要保持的行为。
- 实现必读文件及其用途/相关章节，另列必要的按需地图和上下游入口；不把本角色探索过的全部文档变成下游必读。
- 验证本次行为的已有入口、受影响的直接依赖，以及会改变方案的未决问题。涉及配置或内容工具时指出相关 Schema、编辑/导入说明的实际位置；验证入口可引用项目测试文档的相关部分，不复制完整手册。

区分策划明确要求、已核对项目事实、架构建议和待验证事项；只有现有需求无法决定、且不同选择会改变产品范围、运行语义或公共接口的问题才列为待用户决定。列待决定项前先对照需求原文和适用公共约定；已经明确规定的行为不能再次包装成待用户决定事项。能通过代码/资产核对、已有入口或小范围原型推进的，写成实现期验证项；实现方式、工具载体、数据格式和报告形式属于 Agent 的技术选择，不因涉及新增文件或模块就要求用户先批准。若技术核对后发现没有任何方案能满足已明确需求，再带着证据、影响和最小替代范围回交。架构建议说明依据，不得仅因写入交接就变成强制需求；未被需求或既有公共约定规定的工具、数据格式、接口和报告形式应保留合理实现选择。需求和项目事实引用权威文档，不复制正文；不收录完整源码、原始日志、分析过程或与本次无关的未来设计。文件清单用于导航；实现 Agent 可以核对直接依赖，不因清单漏列一个局部文件就停止。实现发现需要改变需求、公共接口或职责归属时，再回交相应结构问题。

交接只记录对应任务的落点、直接依赖和验证入口。任务入口文档负责映射；不要在入口和架构交接重复任务拆分、依赖或状态，也不要建立完整任务矩阵、排期或重复专题文档。

## 产物与完成边界

每个稳定实现任务维护一份当前有效的架构交接。已有文档或批次目录时沿用原位置；没有时默认使用 `<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/ArchitectureHandoff.md`。总控在任务入口和下游交接中给出任务到文档的确定映射，后续变化在原文档中更新，不按轮次复制。聊天摘要或临时上下文包不能替代该文档；不预建 `LongTerm/`、专题目录或完整基线体系。

只有公共约定确需多人长期共享或存在独立结构决策时，才单独维护相应说明，并由任务交接引用而不复制正文。未发生相关变化时，无需完整冻结基线、放行包、逐条符合性表、未来迁移方案或额外复用案例。

文档已落盘、路径明确，且能交代运行链、复用依据、职责和可执行的改动落点，即可交给实现 Agent；仅阻塞依赖未决问题的部分。以足够支持本次实现为内容边界，不以篇幅或章节数量作为完成标准，也不在本角色中直接实现整个功能。
