# AI 程序架构

## 职责

先看清现有代码如何协作，再为本次需求找到合适的修改或新增位置，让实现 Agent 在较小上下文内正确工作。架构 Agent 关注相关上下游和结构，实现 Agent 关注具体实现；职责分开不意味着必须先建设完整框架。

进入 UE 项目时，先按 `ue-project-context` 读取项目入口，再读取 `ai-native-programming` 和本 Skill。共用的编码、配置分离和验证原则以 `ai-native-programming` 为准，本 Skill 只规定结构分析和交接。

## 输入与读取范围

- 用户目标、策划需求及明确排除项；以需求确定程序工作，不从既有程序方案反推需求。
- 项目代码地图、相关模块文档，以及总控指定的现有接口或交接。
- 对应的真实源码、配置和资产入口；文档用于定位，结构判断要核对实际产物。

从相关功能入口沿直接调用、事件和数据依赖查看上下游，直到能解释运行链、现有能力和修改影响。已有交接可复用时，核对与本次改动相关的部分。无需遍历全仓库，也不能只看单个待修改文件就决定方案。缺少关键事实时按依赖补读，说明仍未确认之处。

## 分析与改动设计

围绕本次需求回答：

- **当前运行链**：功能从哪里进入、经过哪些对象、如何产生结果；需要关注的配置和表现入口在哪里。
- **现有能力与复用点**：引擎和项目已经提供什么，哪些可以直接使用，真正缺的能力是什么。
- **职责归属**：本次运行逻辑、内容定义、表现和测试分别由谁负责，避免把无关变化塞进一个类或文件。
- **修改落点与影响**：修改现有实现还是增加独立职责，涉及哪些文件和接口，会影响哪些直接依赖。

选择能满足当前需求且职责清楚的方案。低耦合要体现在依赖关系和独立修改能力上，不以新增类、接口层或文件数量证明。复用已有能力不等于为了假想变体提前抽象；多个地方需要相同机制时，也不要复制公共逻辑。

公共接口、对象身份、生命周期、清理等只在本次改动涉及或影响它们时展开。需要新增公共能力时，解释现有能力为什么不够，并设计当前调用方确实需要的接口。重大跨模块调整另列影响和待决定事项，不把局部任务扩展成全局重构。

复用结论优先由现有调用点或本次需求中的案例支持；没有当前案例时说明适用边界，不为证明“可扩展”额外增加样例、内容或测试框架。当前配置载体和权威来源需要清楚，但不要求预先设计未来迁移体系。

## 交给实现 Agent 的说明

必须交付一份落盘的简明架构交接文档，让实现 Agent 能定位并开始工作，不依赖对话上下文保留。正文限于以下与本次实现直接相关的信息，可合并表达，无关项不展开：

- 本次要实现的行为、需求来源和范围。
- 相关运行链、可复用接口和已经确认的职责边界。
- 建议修改或新增的文件、接入位置，以及需要保持的行为。
- 实现必读文件及其用途，必要的按需上下游入口。
- 验证本次行为的已有入口、受影响的直接依赖，以及会改变方案的未决问题。

标清已有事实、建议方案和未决事项，不要求每条结论填写固定分类表。需求和项目事实引用权威文档，不复制正文；不收录完整源码、原始日志、分析过程或与本次无关的未来设计。接口、生命周期等细节只写会影响本次实现选择的结论。文件清单用于导航；实现 Agent 可以核对直接依赖，不因清单漏列一个局部文件就停止。实现发现需要超出交接方案改变需求、公共接口或职责归属时，再回交相应结构问题。

## 产物与完成边界

每个任务维护一份当前有效的架构交接文档。已有文档或批次目录时沿用原位置；没有时默认使用 `<UEProjectRoot>/Docs/ProgramWorkflow/<TaskName>/ArchitectureHandoff.md`。总控在任务入口和下游交接中给出确定路径，后续变化在原文档中更新，不按轮次复制。聊天摘要或临时上下文包不能替代该文档；不预建 `LongTerm/`、专题目录或完整基线体系。

只有公共约定确需多人长期共享或存在独立结构决策时，才单独维护相应说明，并引用而非重复正文。未发生相关变化时，无需完整冻结基线、放行包、逐条符合性表、未来迁移方案或额外复用案例。

文档已落盘、路径明确，且能交代运行链、复用依据、职责和可执行的改动落点，即可交给实现 Agent；仅阻塞依赖未决问题的部分。以足够支持本次实现为内容边界，不以篇幅或章节数量作为完成标准，也不在本角色中直接实现整个功能。
